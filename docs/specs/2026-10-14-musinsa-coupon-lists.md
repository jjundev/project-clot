# 무신사 쿠폰가 3만 개 매일 계산: 결론과 제안

상태: **확정 (2026-10-15)**. 구현 계획: [`docs/plans/2026-10-15-musinsa-coupon-registry.md`](../plans/2026-10-15-musinsa-coupon-registry.md)

개정 이력:
- 2026-10-14 초안: 회원 조회 4,000건을 브랜드당 2개씩 나눠 쓰는 방식. 정확도 약 92%.
- 2026-10-15 개정: 쿠폰 번호 순회 방식으로 바꿨다. 정확도 약 99%, 회원 조회 하루 약 260건.
  - 초안이 기댄 전제는 "쿠폰 번호는 회원 조회로만 알 수 있다"였는데, 이 전제가 틀렸다.
  - 초안의 판단과 그 정정은 부록 A에 있다.
- 2026-10-15 확정: 10절의 다섯 가지를 모두 권장값으로 정했다. 구현 세부는 11절에 있다.

근거 문서:
- 검증 보고서: [`docs/verify/musinsa-coupon-plp.md`](../verify/musinsa-coupon-plp.md).
  - 1차(H1~H16)는 쿠폰별 목록을, 2차(H17~H23)는 쿠폰 번호 순회를 검증했다.
  - 재현 스크립트는 `scripts/musinsa-coupon-plp-verify.js`다.
- 쿠폰 API 1차 검증: [`docs/verify/musinsa-coupon-price.md`](../verify/musinsa-coupon-price.md).
- 현재 설계: [`docs/specs/2026-10-14-musinsa-wide.md`](2026-10-14-musinsa-wide.md).

## 1. 질문과 결론

**질문.** 회원 계정이 정지되지 않게 하면서 와이드 스캔 3만 개 상품의 쿠폰가를 하루 안에 모두 알 수 있는가?

**결론.**

| 목표 | 가능 여부 | 이유 |
|---|---|---|
| 3만 개 전부를 매일 정확하게 | **약 99%까지 가능** (계산) | 쿠폰 번호는 연속된 정수다. 쿠폰 목록 API에 번호를 차례로 물으면 쿠폰을 빠짐없이 찾는다(비로그인). 찾은 쿠폰은 쿠폰별 적용 상품 목록으로 3만 개에 적용한다(비로그인, 정확). 남는 1%는 목록 API가 빠뜨린 쿠폰과 오래된 번호의 일부 쿠폰이다. |
| 회원 조회를 줄이면서 | **가능.** 하루 4,000건 → 약 260건 (추정) | 회원 조회는 두 가지에만 쓴다. 새로 찾은 쿠폰이 우리 계정이 쓸 수 있는 쿠폰인지 가리는 판별(하루 약 60건)과, 정확도를 재는 표본(200건)이다. |

**권장.** 쿠폰 번호 순회 방식으로 전환한다.
- 정확도는 약 99%다. 10-14에 뽑은 새 표본 500개로 계산하면 498개(99.6%)가 맞는다. 초안 방식은 92%이고, init의 회원 조회 4,000개로 찾은 쿠폰만 쓰면 82%다.
- 회원 조회가 하루 4,000건에서 약 260건으로 약 15분의 1이 되어 정지 위험이 줄어든다.
- 3만 개 전부의 쿠폰가가 매일 나온다. 2절의 "목록이 금방 NULL이 되는" 문제도 사라진다.
- 틀리는 경우는 모두 쿠폰을 놓쳐 실제보다 비싸게 보이는 쪽이다. 실제보다 싸게 잘못 계산한 경우는 검증에서 0건이었다.
- 대가는 두 가지다.
  - 비로그인 호출이 하루 약 500회에서 약 3,500~4,000회로 는다.
  - 전환할 때 한 번, 약 2시간짜리 별도 실행이 필요하다(6.10).

## 2. 지금 방식과 그 한계

### 2.1 지금 방식

`src/musinsaWide/`:
- 매일 5개 대분류 × 리뷰순 상위 6,000개, 약 3만 개를 비로그인으로 스캔한다.
- 회원 쿠키로 하루 최대 4,000개 상품의 쿠폰을 **상품마다** 조회한다(`COUPON_CHECKS_PER_DAY`). 조회 결과는 상품별 쿠폰 목록으로 저장한다.
- 조회 순서(`store.pickCouponChecks`):
  1. 미조회
  2. 저장 목록에 만료 쿠폰이 있음
  3. 조회 후 가격 변경
  4. 오래된 순
  - 같으면 상품번호순.
- 쿠폰가는 저장 목록으로 매일 로컬 계산한다. 다음 경우에는 NULL이 된다(`applyCouponPrices`).
  - 조회한 지 10일이 넘음(`COUPON_TTL_DAYS`).
  - **저장 목록의 쿠폰이 하나라도 만료됨.** 월말 쿠폰이 한꺼번에 만료될 때 가짜 가격 변동을 막으려는 규칙이다.

### 2.2 한계 1: 첫 바퀴가 8일 걸린다

init(10-14)에서 상품번호가 가장 작은 4,000개만 조회했다. 나머지 26,000개는 조회될 때까지 쿠폰가가 없다. 하루 4,000개씩이라 약 6.5일이 더 걸린다.

### 2.3 한계 2: 짧은 쿠폰 때문에 목록이 금방 NULL이 된다 (10-14 데이터로 확인)

10-14에 조회한 4,000개 중 날짜별로 NULL이 되는 목록:

| 날짜 | NULL이 되는 목록 | 주 원인 |
|---|---|---|
| 10-15 | 2,580 (64.5%) | `359137` 깜짝 쿠폰 5%(10-14 만료, 2,574개), `359271` 기간 한정 맨즈 10%(10-14 만료, 127개) 등 |
| 10-17 | 2,631 (65.8%) | 위 쿠폰 + 10-15~10-16 만료 쿠폰(무탠다드 깜짝 15%·20%, 무탠다드 우먼 깜짝 등) |
| 10-20 | 2,708 (67.7%) | 위 쿠폰 + 행사 쿠폰(10-19 만료) 등 |
| 11-01 | 2,855 (71.4%, 쿠폰이 있는 목록 전부) | 10월 정기 쿠폰(10-31 만료). 4,000개 중 68.4%가 가지고 있다. |

- 미조회 상품이 재조회보다 먼저라서, 이 2,580개는 미조회 26,000개가 끝나는 약 6.5일 뒤에야 다시 조회된다.
- **10-15 실행 뒤 쿠폰가가 있는 상품은 약 5,400개(18%)로 예상된다.** 새로 조회한 4,000개와 10-14 조회 중 NULL이 아닌 1,420개를 더한 수다. 요약의 "쿠폰가 없음" 수가 크게 나올 것이다.
- 1~3일짜리 깜짝 쿠폰이 자주 나오는 한 첫 바퀴 뒤에도 같은 일이 반복된다. 어느 날이든 최근 1~2일 안에 조회한 상품만 쿠폰가를 가지게 된다.

### 2.4 한계 3: 낡은 목록

새 무작위 표본 500개(10-14 조회)에서 "그 뒤에 시작한 쿠폰"을 빼고 최대 쿠폰을 다시 계산했다. 쿠폰이 있는 표본 상품 396개 기준이다.

| 마지막 조회가 | 최대 쿠폰이 달라지는 상품 |
|---|---|
| 1일 전 | 4.0% |
| 2일 전 | 6.8% |
| 4일 전 | 34.6% |
| 8일 전 | 41.9% |

- 하루 4,000개 순환이면 목록의 평균 나이는 약 4일이다.
- 10-14처럼 행사가 몰린 주에는 NULL이 아닌 쿠폰가도 3분의 1가량이 이미 틀린다. 이 비율은 행사 일정에 따라 달라진다.

## 3. 핵심 발견 1: 쿠폰별 적용 상품 목록 API

무신사 쿠폰 페이지("적용 상품 보기")가 쓰는 API다. 쿠폰 페이지 마이크로 프런트엔드(`static.msscdn.net/static/v2/pc/coupon/coupon.js`)에서 찾았다.

```
GET https://api.musinsa.com/api2/coupon/plp/v1/goods
    ?couponNo=<쿠폰 번호>&couponKind=PRODUCT&caller=COUPON&gf=A
    &category=001,002,003,103,004&sortCode=REVIEW&page=<n>&size=300
```

같은 파라미터로 `/plp/v1/goods/count`를 부르면 개수만 준다(`data: <숫자>`).

### 3.1 검증한 성질

| 성질 | 결과 |
|---|---|
| 로그인 필요 여부 | 필요 없다. 쿠키를 보내도 결과가 같다(4종: 개수, 첫 페이지 상품과 순서 동일). 쿠키를 보내도 상품의 `couponPrice`는 null이라 회원 대상 여부는 알 수 없다. |
| `couponKind` | `PRODUCT`만 동작한다. 상품 페이지 링크가 쓰는 `CART`는 모든 쿠폰에서 0건이고, 그 밖의 값은 400이다. |
| 정확도 | 회원 조회로 확인한 쿠폰 보유 18,589쌍 중 18,585쌍이 목록에 있다(99.98%). 목록에만 있는 쌍(잘못 포함)은 0이다. |
| 예외 | 396종 중 3종(모두 "10월 이달의 ○○ 6% 쿠폰")은 목록이 비었거나 일부 상품이 빠졌다(`354094` 미즈노, `355780` 토앤토, `355216` 밸롭). |
| 최소금액 | 목록이 이미 거른다. 최소금액이 있는 쿠폰 94종의 목록 상품 75,317개 중 최소금액 미만은 0이다. |
| 쿠폰 조건 | 율, 상한, 최소금액, 만료일은 상품마다 다르지 않다(396종 모두). 그래서 한 상품에서 얻은 조건을 목록 전체에 적용할 수 있다. 할인액 식은 500/500 일치. 단, 조건은 회원 조회로만 얻는다. 목록에는 조건이 없다. |
| 만료 | 끝난 쿠폰도 수십 분은 목록에 남는다. 10-14에 끝난 쿠폰이 10-15 00:00:57에 488,847개였고 00:24에는 0개였다(14종 모두). 만료는 조건의 만료일로 판단해야 한다. |
| 페이지 크기 | 최대 300. **301 이상이면 오류 없이 빈 목록(totalCount 0, SUCCESS)이 온다.** |
| 깊은 페이지 | 상한 없음. 80만 번째 상품까지 응답했다. |
| 정렬 | 리뷰순 순서가 카테고리 목록과 같다. 이웃한 범위 안 상품 130,347쌍 중 역순은 110쌍(0.08%)이다. 두 목록 모두 화면에 보이는 리뷰 수 순서와는 조금 어긋난다(캐시된 값으로 정렬하는 것으로 보임). |
| 범위 경계에서 멈추기 | "페이지 마지막 상품의 리뷰 수 < 그 대분류 범위의 최저 리뷰 수"이면 멈춘다. 이 규칙 때문에 놓친 쌍은 0이다. |
| 호출량 | 쿠폰 396종에 1,182회, 378초(2개 병렬, 호출 간격 0.5초). 전부 HTTP 200, 429 0건. |

### 3.2 무엇이 달라지는가

- 이전 질문은 "이 상품에 어떤 쿠폰이 붙나?"였다. 3만 개 상품마다 회원 조회가 필요했다.
- 이제는 "이 쿠폰은 어떤 상품에 붙나?"를 쿠폰마다 비로그인으로 물으면 된다.
- 남는 문제는 **어떤 쿠폰이 있는지 아는 것(쿠폰 발견)** 하나다. 4절이 이 문제를 푼다.

## 4. 핵심 발견 2: 쿠폰 번호 순회

### 4.1 쿠폰 번호는 연속된 정수다

- 지금까지 회원 조회로 본 쿠폰 396종 중 384종의 번호가 350,000~360,000 사이에 있다.
- 10-15 00:01 기준으로 가장 큰 번호는 360,209다. 10-14 23:51에도 같았다(밤사이 변화 없음).
- 번호는 하루 약 377개씩 는다. 표본 쿠폰의 시작일별 최대 번호를 보면 09-16에 349,552, 10-14에 360,102다. 시작일은 만든 날보다 늦을 수 있어 대략값이다.
- 오래된 번호에도 살아 있는 쿠폰이 있다. 대부분 2029년까지 유효하고 적용 상품이 날마다 바뀌는 "오늘의 깜짝 N%" 묶음이다.
  - 해당 번호: 252,561~252,562, 285,522, 334,340~334,343, 349,552
  - 그 밖에 `133734` 데상트 5%(2026-12-31까지), `326028` 반스 20%도 있다.

### 4.2 count API로 번호를 훑는다

count API는 쿠키 없이 아무 번호에나 답한다. 없는 번호(99,999,999)는 0을 준다. 네 구간의 번호 1,744개를 조회했다(482초, 2개 병렬, 호출 간격 0.5초, 모두 200).

| 구간 | 상품 있는 번호 | 아는 쿠폰 (그중 상품 있음) | 처음 보는 번호 |
|---|---|---|---|
| 359,500~360,600 (최신) | 457 (발급된 710개 중 64%) | 9 (9) | 448 |
| 353,170~353,210 (회원 정기 쿠폰 근처) | 36 / 41 | 4 (4) | 32 |
| 349,400~349,700 (9월 중순) | 13 / 301 (4%) | 1 (1) | 12 |
| 334,200~334,500 (8월 초) | 5 / 301 (2%) | 2 (2) | 3 |

- **놓치지 않는다.**
  - 구간 안의 아는 쿠폰 16종은 모두 상품이 있다고 나왔다.
  - 4.3의 회원 조회가 돌려준 쿠폰 중 구간 안에 있는 24종도 모두 상품이 있다고 나왔다.
- 오래된 구간에 상품 있는 번호가 적은 이유는 만료된 쿠폰이 빠지기 때문이다.
- 상품 있는 번호 사이의 빈 번호는 최신 구간에서 가장 길어야 15개 연속이었다.

### 4.3 우리 계정 쿠폰 가려내기 (판별)

찾은 쿠폰 대부분은 우리 계정이 쓸 수 없는 쿠폰이다(다른 등급용, 특정 회원용).
- 처음 보는 번호 495개 중, 첫 페이지(리뷰순 300개)에 10-14 스캔의 3만 개 범위 상품이 있는 번호는 227개다. 나머지는 우리 가격에 영향이 없다.
- 회원 조회는 상품 하나에 붙는 쿠폰을 모두 돌려준다. 그래서 판별할 번호들의 첫 페이지에 가장 많이 겹치는 상품부터 조회했다. **227개를 회원 조회 114회로 모두 판별했다.**
- 결과: 쓸 수 있음 16, 대상 아님 211.
  - 대상 아님에는 전 상품(50만 개 이상)에 붙는 회원 정기 쿠폰 30종이 있다. 다른 등급용으로 보인다. 우리 등급(실버)의 4종은 이미 아는 쿠폰이다.
  - 쓸 수 있음의 예: 캘빈클라인 20%(3종), 언더아머 20%, 스파오 깜짝 30%, 미쏘 20%, 오늘의 깜짝 10%(`334342`).
- 같은 114회 조회에서 쓸 수 있는 쿠폰이 85종 더 나왔다. 아는 쿠폰도 아니고 순회 구간 밖에 있던 쿠폰이다. 실제 쿠폰은 지금까지 아는 396종보다 훨씬 많다.
- 날짜가 바뀐 뒤(10-15 00:03) 대상 아님 중 359,900 이상인 93개를 회원 조회 58회로 다시 판별했다. 쓸 수 있게 바뀐 번호는 0이다. 시작일 전이라 안 나온 쿠폰이 섞이지 않았다는 뜻이다.

### 4.4 정확도 (계산)

전제는 "구간 안의 번호를 모두 판별하면, 우리 계정이 쓸 수 있는 구간 안 쿠폰은 모두 찾는다"(4.2, 4.3)이다. 이 전제로 새 표본 500개의 최대 쿠폰 할인액을 계산했다.

| 쿠폰을 찾는 방법 | 하루 회원 조회 | 정확 |
|---|---|---|
| init 4,000개에서 찾은 쿠폰 (비교) | 4,000 | 82.2% |
| 브랜드당 2개 (초안) | 3,128 | 92.1% |
| 번호 350,000~360,209 순회 | 약 260 | 99.0% (495/500) |
| **번호 345,000~360,209 순회 + init에서 찾은 쿠폰** | **약 260** | **99.6% (498/500)** |
| 번호 325,000~360,209 순회 | 약 260 | 99.8% (499/500) |

- 놓친 2개는 `334341` 오늘의 깜짝 15%(오래된 번호)와 `354094` 미즈노(목록 누락)다.
- 실제보다 싸게 계산한 경우는 모든 경우에 0이다.
- 브랜드당 2개 행은 같은 브랜드 조회 상품이 있는 표본 278개로 잰 값이다(부록 B).

## 6. 제안 설계

### 6.1 하루 흐름

| 단계 | 내용 | 호출 (추정) | 시간 (추정) |
|---|---|---|---|
| 1. 목록 스캔 | 지금과 같다. 3만 개, 비로그인. 각 상품의 리뷰 수도 저장한다(범위 경계용). | 비로그인 500 | 약 1분 |
| 2. 번호 순회 | 새 번호와 최근 3일 치 빈 번호의 count를 묻는다(6.2). | 비로그인 약 1,000 | 약 5분 |
| 3. 새 쿠폰 판별 | 상품이 있고 등록부에 없는 번호의 첫 페이지를 읽는다. 3만 개 범위에 걸리는 번호만 회원 조회로 판별한다(6.3). | 비로그인 약 240, 회원 약 60 (상한 200) | 약 2분 |

- 하루 합계(추정): 회원 약 260회(상한 400), 비로그인 약 3,500~4,000회.
- 4단계는 5단계와 동시에 돌린다. 4단계에서 새로 찾은 쿠폰은 5단계가 끝난 뒤 이어서 순회한다.
- 전체 약 20분이다. 지금의 실행 예산(35분, 작업 제한 45분) 안에 들어간다.
- 비로그인 호출은 검증과 같은 속도(2개 병렬, 호출 간격 0.5초)로 한다. 429가 나면 그 단계를 멈추고 전날 결과를 쓴다.

### 6.2 번호 순회

- **새 번호.** 등록부의 가장 큰 번호 다음부터 count를 묻는다.
  - 상품 없는 번호가 200개 이어지면 멈춘다. 검증 구간 안의 가장 긴 공백은 15개였다.
  - 큰 공백에 대비해, 멈춘 뒤 +500, +1,000, +2,000 번호를 하나씩 더 묻는다. 상품이 있으면 거기까지 이어서 훑는다.
  - 회원 조회 결과에 등록부의 가장 큰 번호보다 큰 쿠폰이 나와도 그 번호까지 이어서 훑는다.
- **최근 빈 번호 재조회.** 최근 3일 안에 생긴 번호 중 count가 0이던 번호를 다시 묻는다. 만든 뒤 상품이 늦게 붙는 쿠폰에 대비한 것이다(미확인).
- count에는 5개 대분류 필터를 건다. 상품이 있고(count > 0) 등록부에 없는 번호가 3단계로 간다.
- 오래된 번호는 매일 다시 훑지 않는다. 오래된 번호의 쿠폰은 6.3의 이웃 조회와 6.4의 표본으로 찾는다.

### 6.3 새 쿠폰 판별

- 3단계 대상 번호마다 첫 페이지(리뷰순 300개)를 비로그인으로 읽는다.
  - 3만 개 범위의 상품이 없으면 "범위 밖"으로 두고 판별하지 않는다.
    - 첫 페이지는 리뷰가 가장 많은 300개라서, 여기에 범위 상품이 없으면 나머지 상품에도 없다.
    - 쿠폰이 살아 있는 1~3주 사이에 그 상품이 범위에 들어오는 일은 드물다. 들어오더라도 표본 조회에 그 쿠폰이 나오면 쓸 수 있음으로 바뀐다.
  - 범위의 상품이 있으면 판별 대기로 둔다.
- **판별.**
  - 판별 대기 번호들의 첫 페이지에서 범위 안이고 품절이 아닌 상품을 고른다. 가장 많은 대기 번호에 걸친 상품부터 고르고, 같으면 리뷰가 많은 상품을 고른다.
  - 고른 상품을 회원 조회한다. 그 상품에 걸친 대기 번호는 모두 판별된다.
    - 조회 결과에 있으면 **쓸 수 있음**이다. 조건(율, 상한, 최소금액, 시작일, 만료일)을 저장한다.
    - 없으면 **대상 아님**이다.
  - 검증에서는 227개를 114회로 판별했다.
- 하루 판별 상한은 회원 조회 200회다. 넘치는 번호는 다음 날 상품 수가 많은 번호부터 판별한다. 요약에 대기 수를 표시한다.
- 회원 조회(판별·표본) 결과에 나온 쿠폰은 모두 등록부에 반영한다.
  - 대상 아님이던 쿠폰도 다시 나오면 쓸 수 있음으로 바꾼다. 날짜가 바뀌어 시작한 쿠폰이나 회원군이 바뀐 쿠폰을 이렇게 잡는다.
  - 검증에서는 판별 조회 114회에서 모르던 쿠폰 85종이 함께 나왔다.
- **이웃 조회.** 순회 구간보다 오래된 번호의 쿠폰이 회원 조회에 나오면 그 번호 ±50의 count도 묻는다. 같은 묶음의 쿠폰(예: 오늘의 깜짝 5%·10%·15%)을 함께 찾기 위한 것이다.

### 6.4 표본 조회

- 3만 개 중 무작위 200개를 고른다. 대분류마다 40개씩이고, 품절은 뺀다. 날짜로 시드를 정해 다시 뽑을 수 있게 한다.
- 용도:
  1. 정확도 측정(6.9).
  2. 등록부에 없는 쿠폰 발견. 오래된 번호의 쿠폰과 목록 누락 쿠폰을 찾는다.
  3. 쿠폰 생존 확인(6.8).
- 조회 결과는 지금처럼 상품별 쿠폰 목록으로도 저장한다(6.7의 직접 조회 결과).

### 6.5 쿠폰 등록부

번호마다 하나의 상태를 가진다.

| 상태 | 뜻 | 다음 처리 |
|---|---|---|
| 쓸 수 있음 | 우리 계정 회원 조회에 나온 쿠폰. 조건을 안다. | 만료일까지 매일 목록을 순회한다. |
| 대상 아님 | 판별 조회에 안 나온 쿠폰 | 다시 판별하지 않는다. 다른 회원 조회에 나오면 쓸 수 있음으로 바꾼다. |
| 판별 대기 | 상품이 있고 범위에 걸리지만 아직 판별하지 않은 번호 | 다음 판별에서 먼저 처리한다. |
| 범위 밖 | 상품이 있지만 첫 페이지에 범위 상품이 없는 번호 | 판별하지 않는다. 회원 조회에 나오면 쓸 수 있음으로 바꾼다. |
| 퇴출 | 쓸 수 있음이었지만 생존 관리(6.8)에서 빠진 쿠폰 | 회원 조회에 다시 나오면 되살린다. |
| 빈 번호 | count 0 | 최근 3일 치만 보관하고 다시 묻는다. |

- 쓸 수 있음 쿠폰은 만료일이 지나면 순회하지 않는다.
- 대상 아님과 범위 밖 번호는 기록으로 남기고 60일 뒤 지운다. 번호 순회는 오래된 번호를 다시 묻지 않으므로, 이 번호들은 회원 조회에 나올 때만 바뀐다.
- 처음 본 날, 마지막으로 회원 조회에 나온 날, 판별일, 최근 count를 함께 저장한다.

### 6.6 쿠폰 목록 순회

- 대상: 등록부에서 쓸 수 있음 상태이고 만료일이 오늘 이후인 쿠폰.
- 5개 대분류 안의 상품이 3,000개 이하인 쿠폰은 목록 전체를 대분류 필터(`category=001,002,003,103,004`)로 한 번에 읽는다. 평균 1.83페이지다.
- 그보다 많은 쿠폰(회원 정기 쿠폰, 깜짝 쿠폰 등)은 대분류마다 리뷰순으로 읽는다.
  - 마지막 상품의 리뷰 수가 오늘 그 대분류 범위의 최저 리뷰 수보다 작아지면 멈춘다.
  - 스캔과 순회 사이의 시간차에 대비해 한 페이지를 더 읽는다.
  - 회원 정기 쿠폰은 쿠폰당 약 77페이지다.
- 페이지 크기는 300으로 고정한다. 응답 개수가 0인데 그 쿠폰을 가진 조회 상품이 있으면 오류로 본다(크기 오류나 API 변경 감지).
- 오늘의 쿠폰별 적용 상품을 저장한다. 오늘 것만 유지한다.
- 순회가 실패(429, 시간 초과)한 쿠폰은 전날 결과를 쓰고 요약에 표시한다.
- 호출량은 쿠폰 수에 비례한다. 검증 값은 "대분류별로 읽는 큰 쿠폰 24종에 503회 + 나머지 쿠폰당 1.83회"였다. 쓸 수 있는 쿠폰이 700~1,000종이면 하루 약 1,700~2,300회다.

### 6.7 쿠폰가 계산

상품마다 다음 쿠폰을 모은다.
1. 등록부의 쓸 수 있는 쿠폰 중 오늘 적용 상품 목록에 이 상품이 있는 쿠폰.
2. 이 상품을 직접 조회한 결과(10일 이내) 중 만료되지 않은 쿠폰. 3.1절의 목록 예외 같은 경우를 메운다.

모은 쿠폰의 최대 할인을 `couponDiscountMusinsa`로 계산한다. 쿠폰가 = 판매가 − 추가할인 − 최대 할인.
- **만료된 쿠폰은 그 쿠폰만 뺀다.** 목록 전체를 NULL로 만들지 않는다. 다른 쿠폰은 목록 순회로 매일 다시 확인되므로, 지금 방식의 "가짜 변동 방지용 NULL"이 필요 없다.
- 만료는 조건의 만료일로 판단한다. 끝난 직후의 목록에 남은 쿠폰도 이렇게 걸러진다(3.1 만료).
- 퇴출된 쿠폰은 쓰지 않는다.
- 판매가가 없으면 NULL이다(지금과 같음).

### 6.8 생존 관리

다 쓴 쿠폰이나 선착순 소진 쿠폰은 목록에는 남아 있어도 회원 조회에서는 사라질 수 있다.
- 최근 7일 동안 그 쿠폰의 적용 목록에 있는 상품을 회원 조회한 결과가 3건 이상이고 그 쿠폰이 한 번도 나오지 않았다면, 그 쿠폰을 퇴출한다.
- 같은 쿠폰이 다시 조회에 나오면 되살린다.
- 회원 조회가 하루 약 260건으로 줄어서 관찰이 적다. 그래서 하루가 아니라 7일 치를 모아서 본다.
- 10-14 당일 검증에서는 init에서 본 쿠폰이 두 시간 뒤 사라진 경우가 2,169쌍 중 0이었다. 여러 날에 걸친 변화는 운영하면서 이 규칙으로 잡는다.

### 6.9 정확도 측정과 요약

- **정확도.** 표본 200개마다 두 값을 비교한다.
  - 직접 조회를 빼고 목록만으로 계산한 최대 할인
  - 실제 최대 할인
  - 정확, 낮게 예측, 높게 예측 건수와 놓친 이유를 요약에 넣는다. 놓친 이유는 등록부에 없는 쿠폰, 목록 누락, 퇴출 오판이다.
  - 99%가 맞는지 매일 확인된다. 200개라 하루 값은 ±1.4%p 정도 흔들린다.
- **요약에 추가할 줄:**
  - 번호 순회: 새 번호 수, 가장 큰 번호, 0에서 양수로 바뀐 번호 수
  - 판별: 회원 조회 수, 쓸 수 있음, 대상 아님, 대기
  - 등록부: 쓸 수 있는 쿠폰 수(새로 찾음, 만료, 퇴출)
  - 목록 순회: 호출 수와 실패
  - 쿠폰가가 있는 상품 수
- **쿠폰가 하락 알림.** 하락 원인이 "오늘 처음 찾았지만 시작일은 이전인 쿠폰"이면 알림에서 빼거나 따로 표시한다. 쿠폰을 늦게 찾아서 생긴 가짜 하락이기 때문이다. 번호 순회로 대부분 첫날 찾으므로 드물 것이다.

### 6.10 전환 (1회)

1. 등록부를 채운다. 현재 DB의 상품별 쿠폰 목록에 있는 쿠폰 중 만료 전인 것을 쓸 수 있음으로 넣는다.
2. 번호 345,000부터 가장 큰 번호까지 약 15,200개의 count를 묻는다. 비로그인으로 약 70분이다.
3. 상품이 있는 번호의 첫 페이지를 읽고 판별한다(6.3).
   - 첫 페이지: 비로그인 약 4,000~5,500회 (추정)
   - 판별: 회원 약 800~1,200회 (추정)
   - 추정의 바탕은 다음과 같다.
     - 350,000~359,500의 상품 있는 번호 비율을 40~60%로 봤다(10월 쿠폰이 대부분 아직 유효함).
     - 범위에 걸리는 비율 43%와 번호당 판별 비용 0.57회는 최신 구간 값이다.

5. 다음 날부터 매일 흐름(6.1)으로 돈다.

### 11.4 6절에 더한 규칙

- **전환 전에는 쿠폰가를 계산하지 않는다.** `backfill_done`이 없으면 2~5단계를 건너뛰고 쿠폰가를 모두 NULL로 둔다. 요약에는 "쿠폰 등록부 미완성 — backfill 필요"라고 쓴다. 등록부가 반쯤 찬 상태로 계산하면 쿠폰 없는 가격이 쿠폰가로 공개되기 때문이다.
- **등록부로 처음 계산한 날에는 쿠폰가 하락 알림을 보내지 않는다.** 그날은 상품별 목록에서 쿠폰별 목록으로 바뀌면서 가격이 한꺼번에 움직인다. 요약에 "등록부 전환 첫날 — 쿠폰가 하락 알림 생략"이라고 쓴다.
- **전환 실행은 빈 번호를 저장하지 않는다.** 345,000부터 훑으면 빈 번호가 수천 개 나온다. 이것을 다시 묻는 것은 일상 실행에서 새로 생긴 번호만이다.
- **늦게 찾은 쿠폰의 판정.** 오늘 최대 할인을 준 쿠폰이 오늘 처음 등록부에 들어왔고 시작일이 오늘보다 이르면, 그 하락은 늦게 찾은 쿠폰 때문인 것으로 본다.
- **표본 정확도의 기준.** 판별이 끝난 시점의 쓸 수 있는 쿠폰만으로 예측한다. 그래서 표본 조회에서 처음 찾은 쿠폰은 예측에 들어가지 않는다. 놓친 이유는 등록부에 없음, 목록에 없음, 퇴출 오판의 세 가지로 나눈다.
- **판별할 수 없는 쿠폰.** 판별 대기 쿠폰의 범위 상품이 모두 품절이 되었거나 범위를 벗어나면 범위 밖으로 바꾼다.

| 10-14, 첫 답변 | 회원 조회 1,000건이면 약 97% | 같은 4,000개 안에서 찾고 맞힌 값이라 부풀려졌다. 새 표본으로는 79%다. 철회한다. |
| 10-14, 초안 | 100%는 불가능하다. 회원 조회 4,000건을 브랜드당 2개로 쓰면 약 92%가 최선이다. | 전제("쿠폰 번호는 회원 조회로만 알 수 있다")가 틀렸다. 번호 순회로 약 99%, 회원 조회 약 260건이다. |
| 10-15, 답변 | 최신 구간 번호의 41%가 쿠폰이다. | 아직 발급되지 않은 번호까지 분모에 넣은 값이다. 발급된 번호 기준으로는 64%다. |

## 부록 B. 상품을 조회해서 쿠폰을 찾을 때의 정확도 (비교용)

번호 순회 없이 회원 조회로 쿠폰을 찾을 때, 새 표본 500개의 최대 쿠폰 할인액을 "찾은 쿠폰 + 쿠폰별 목록"으로 맞힌 비율이다.

| 쿠폰을 찾는 방법 | 하루 회원 조회 | 정확 |
|---|---|---|
| 무작위 500개 | 500 | 76.2~77.8% |
| 무작위 1,000개 | 1,000 | 78.4~79.2% |
| 무작위 2,000개 | 2,000 | 80.8~82.0% |
| init 4,000개 (상품번호순) | 4,000 | 82.2% |
| 브랜드당 1개 | 1,803 | 88.2% |
| 브랜드당 2개 | 3,128 | 92.1% |
| 브랜드당 3개 | 4,247 | 93.6% |

- 브랜드 단위 행은 같은 브랜드의 다른 조회 상품이 있는 표본으로 잰 값이다. 여러 상품에 붙는 쿠폰(상품 50개 이상에서 본 21종)은 어느 조회로든 찾는다고 가정했다.
- 놓친 경우는 모두 "모르는 쿠폰" 때문이다. 쿠폰은 브랜드 정기 쿠폰과 행사 쿠폰이 많다. 그래서 상품 조회로는 브랜드와 행사를 고르게 덮어야 하고, 그래도 92% 근처에서 멈춘다.

## 부록 C. 확인한 다른 경로

쿠폰 번호를 회원 조회 없이 알아내려고 확인한 경로다. 번호 순회 외에는 쓸 수 없었다.

| 경로 | 결과 |
|---|---|
| 로그인한 카테고리 목록 | 회원 쿠폰가가 없다. 120개에서 비로그인 응답과 같았다. |
| 브랜드 쿠폰 API `api2/coupon/coupons/available-brand-coupon?brandId=` | 비로그인 경로(`/public/...`)는 빈 목록이다. 회원 경로는 무신사 스탠다드 1종, 뉴발란스 0종이다. 그 브랜드 상품에 실제로 붙는 행사 쿠폰(SG)이 빠져 있다. |
| 웹 설정의 `enableCouponMemberBulkApi: true` | 이름으로 보아 회원 쿠폰 일괄 조회일 수 있다. 그러나 상품, 브랜드, 카테고리 페이지 번들과 지연 로드 청크 145개, 마이크로 프런트엔드 8개 어디에도 호출 코드가 없다. 앱 전용일 수 있으며 미확인이다. |
| 회원 쿠키를 붙인 쿠폰 목록 | 상품의 `couponPrice`가 null이다(4종). 회원 대상 여부를 알 수 없다. |
| **쿠폰 목록 count API로 번호 순회** | **쓸 수 있다(4절).** |


### 11.5 최종 리뷰 보완 (2026-10-15)

- 일상 순회의 `frontier`는 완전히 조회된 배치의 마지막 양성 번호까지만 전진한다. 병렬 작업의 낮은 번호가 실패하면 그 배치를 다음 실행에서 다시 조회한다.
- 목록 순회는 각 페이지와 재시도 전에 마감·다른 작업자의 429를 확인한다. 중단된 쿠폰은 부분 목록으로 덮어쓰지 않고 이전 목록을 유지한다.
- 판별 200회·표본 200회·이웃 count 300회의 한도는 한국 날짜별로 `meta`에 저장한다. 실제 HTTP 시도 직전에 차감하므로 실패·인증 재시도도 한도에 포함되며, 같은 날짜 재실행은 남은 한도만 쓴다. 전환 판별의 1,500개 한도는 기존 실행 단위를 유지한다.
- 회원 조회에서 반환된 쿠폰은 PLP 적용 목록의 누락 여부와 관계없이 양성 생존 관찰을 기록한다. 반환되지 않은 쿠폰의 음성 관찰은 해당 상품이 PLP에 포함된 경우에만 기록한다.
- 가격 계산의 직접 조회 보완과 표본 정확도의 예측·실측 모두 시작일과 만료일을 확인한다.
