# 4910 랭킹 상위 100개 브랜드 × 우수 셀러 가격 추적 — 설계

Source: 2026-10-10 ~ 10-11 조사 세션. 조사 근거는 `docs/verify/4910-member-price.md`.
사용자가 정한 항목은 **[confirmed]**, 기본값을 제안한 항목은 **[default]**로 표시한다(§Decisions).

## Intent
지금은 유니클로·GU 판매글 전체(15.9k)를 `daily` 안에서 스캔해 `data/4910.db`로 커밋한다.
이것을 다음과 같이 넓힌다.
- 대상: **4910 브랜드 랭킹 상위 100개 브랜드**
- 필터: **구매만족도 95% 이상, 리뷰 100개 이상인 셀러의 판매글만**
- 가격: 목록가와 함께 **내 쿠폰함 기준 쿠폰가**를 매일 계산

규모가 커져(추정 19만 건, DB 약 106MB) git 커밋은 쓸 수 없다. 그래서 DB는 **GitHub Release 첨부 파일**에 두고, 수집은 **별도 workflow**에서 돌린다.

완료 기준
- 스케줄 실행 한 번이 상위 100개 브랜드를 완전 스캔하고, 우수 셀러 판매글의 목록가·쿠폰가를 기록한 DB를 Release에 올린다.
- 텔레그램 일일 요약 1통이 온다.
- Pages 대시보드의 `4910 전체`에서 브랜드를 골라 볼 수 있다.
- 4910 수집이 실패해도 무신사 daily와 Pages 배포는 영향받지 않는다.

Classification: architectural — 저장소 위치(git → Release), 실행 단위(daily 단계 → 별도 workflow), 규모(12배), 대시보드 데이터 분할이 모두 바뀐다.

## Behavior when done
- **새 workflow `.github/workflows/4910.yml`**
  - 매일 10:30 KST(01:30 UTC)에 돈다. 무신사 daily(09:30) 이후다.
  - `workflow_dispatch`로 `probe` / `scan`을 고를 수 있다.
  - 순서: Release에서 DB 내려받기 → 브랜드 목록 확인 → 스캔 → 셀러 판정 → 쿠폰 판정 → 기록 → DB 올리기 → 텔레그램.
- **CLI 명령**
  - `node src/cli.js track-4910`: 상위 100개 브랜드 전체.
  - 옵션 `--brand <sno>`, `--dry-run`, `--concurrency=1-4`(기본 3).
  - `node src/cli.js 4910-db pull|push`: 로컬 개발용으로 Release DB를 받거나 올린다.
- **`daily`에서 4910 단계를 뺀다.** `--skip-4910`은 호환용으로 남기되 아무 일도 하지 않는다. 찜 동기화도 새 workflow로 옮긴다.
- **텔레그램 1통/일**
  - 스캔 브랜드 수, 판매글 수, 통과 셀러 수, 신규·가격변동·종료 수
  - 직전 기록가 대비 **10% 이상 하락** 상위 10개
  - 찜 상품 쿠폰가 하락
  - 쿠폰함 변화(새 쿠폰, 만료)
- **대시보드**: `4910 전체` 칩을 누르면 브랜드 선택 목록이 뜬다. 고른 브랜드의 데이터 파일만 불러온다(§5).
- **실패 처리**
  - Release DB를 내려받지 못하면 **스캔을 중단한다.** 빈 DB로 시작하면 모든 판매글이 신규로 잡히고 이력이 덮인다.
  - 일부 브랜드가 불완전 스캔이면, 그 브랜드의 판매글은 miss를 세지 않는다(지금 규칙과 같음).
  - 업로드에 실패하면 job을 실패로 끝낸다. Release의 직전 DB는 그대로 남는다.

## Not in this round
- 판매자 온도 — 스크립트로 얻을 수 없다(Cloudflare). 대체 지표로 구매만족도를 쓴다.
- 상위 100개 밖의 브랜드, 브랜드가 없는 판매글
- 셀러 간 같은 제품 묶기
- 포인트를 뺀 "예상 구매가" — 포인트 잔액은 텔레그램 요약에만 표시한다.
- 무신사 쪽 변경

## Implementation spec

### 1. 브랜드 목록 — `src/site4910/brands.js` (신규)
- `fetchTopBrands(client, n = 100)`: 랭킹 API를 `last_sno`로 넘기며 상위 `n`개의 `{ sno, name }`을 받는다.
- 결과는 `brands` 테이블(`sno, name, rank, first_ranked_date, last_ranked_date, active`)에 저장한다.
- **목록 갱신은 주 1회(월요일)**만 한다. 다른 날은 저장된 `active=1` 목록을 쓴다. 이유는 랭킹이 날마다 조금씩 바뀌어 판매글이 들락날락하면 종료 판정이 흔들리기 때문이다.
- 상위 100에서 빠진 브랜드는 `active=0`이 되고 그 판매글은 `status='OUT_OF_SCOPE'`가 된다. DROPPED와 다르고 miss도 세지 않는다.
- 유니클로(2421)와 GU(13647)는 순위와 관계없이 항상 포함한다(`PINNED_BRANDS_4910`).

### 2. 스캔 — `src/site4910/client.js`, `track.js`
- 기존 `scanBrand`(가격 구간 이분 분할, 구간당 ≤ 2,500)를 그대로 쓴다.
- 브랜드 단위 병렬 처리를 추가한다. 동시 실행 수는 기본 3이다. 요청 간격 300ms는 작업자별로 유지한다.
- 전체 예산은 `BUDGET_MS_4910 = 25분`이다. 예산을 넘기면 남은 브랜드는 불완전 스캔으로 처리한다.
- 저장하는 목록 행에 `market_type_sno`(`logging.analytics.MARKET_TYPE_SNO`)를 추가한다.

### 3. 셀러 판정 — `src/site4910/sellers.js` (신규)
- `markets` 테이블: `sno, name, satisfaction, reviews_count, is_official, checked_date, qualified`
- 판정: `qualified = satisfaction >= 95 && (reviews_count ?? 0) >= 100` **[confirmed]**
- 조회 대상
  - 스캔에서 처음 본 셀러는 즉시 조회한다.
  - 기존 셀러는 `checked_date`가 7일 넘게 지났을 때 다시 조회한다.
  - 하루 조회 수 상한은 300건이다(초과분은 다음 날).
  - 셀러 약 760곳 기준으로 하루 평균 약 110건, 비로그인 요청이다.
- `applyScan`에 넘기기 전에 **qualified 셀러의 판매글만 남긴다.**
  - 셀러가 탈락하면 그 판매글은 `status='OUT_OF_SCOPE'`(miss 안 셈)가 된다.
  - 셀러가 다시 통과하면 판매글은 `REVIVED` 이벤트로 돌아온다.
- 결과적으로 유니클로·GU도 이 필터를 받는다. 15.9k에서 약 6.6k로 줄어든다(21곳 통과). 걸러진 기존 판매글은 첫 실행 때 `OUT_OF_SCOPE`로 바뀌고 이력은 남는다.

### 4. 쿠폰가 — `src/site4910/coupons.js` (신규)
- 헤더: `X-App-Type: AGLO`, `X-App-Version: 0.1.0`, `X-Device-Type: PCWeb`, `Authorization: JWT $ABLY_JWT_TOKEN`
- **쿠폰함**
  - `GET /aglo/api/members/me/coupons/`에서 `is_usable && is_in_available_period`인 쿠폰을 쓴다.
  - 퍼센트 쿠폰과 정액 쿠폰을 모두 다룬다. 최소금액은 `conditions[1]`에서 파싱한다.
  - 저장 위치는 `wallet_coupons(coupon_sno, name, type, percent, price, max, min, finished_at, seen_date)`이다.
- **판매처별 적용 여부**
  - qualified 셀러마다 판매글 2개를 고른다. 하나는 가장 싼 1만 원 이상 상품, 다른 하나는 가장 비싼 상품이다.
  - 옵션 번호는 비로그인 `GET /api/v2/goods/{sno}/` → `goods.linked_option.sno`에서 얻는다.
  - 그 옵션으로 `GET /aglo/api/coupons/best-coupon?options=[{"sno":opt,"ea":1}]`를 호출한다.
  - 결과는 `market_coupons(market_sno, date, coupon_sno|null, coupon_name, checked_price, coupon_discount)`에 저장한다. 1만 원 미만은 쿠폰 최소금액에 걸려 판정에 쓸 수 없으므로 저가 표본도 1만 원 이상으로 고른다.
  - 쿠폰함에 없는 판매처 전용 쿠폰(예: TNGT 5%)이 나오면 그 판매처 전용으로 `wallet_coupons`에 추가한다.
  - 하루 요청 수는 218곳 × 2개 × 2건 = 약 870건이다. 로그인 요청은 약 440건이다.
- **계산**
  - 판매처에 쿠폰이 하나라도 적용되면, 그 판매처에 적용되는 쿠폰 집합 = 쿠폰함 전체(+ 판매처 전용)로 본다(검증상 전부 아니면 전무).
  - 쿠폰가 = `ceil10(L − max over 쿠폰 min(max, floor(L·%/100)))`이다. `L < 최소금액`인 쿠폰은 빼고, 결과가 L보다 크면 L로 둔다.
  - 고가 표본의 실제 할인과 계산이 다르면 그 판매처를 `coupon_mismatch`로 표시하고, 요약에 경고를 남긴다(자가 검증).
- **저장**
  - `goods.coupon_price`에 그날 값을 쓴다.
  - `price_changes`에는 쓰지 않는다. 쿠폰이 바뀌는 날 전 판매글에 이벤트가 생기는 것을 막기 위해서다.
  - 쿠폰가 이력은 `coupon_daily(date, market_sno, coupon_sno)`만으로 재구성할 수 있다.
- **토큰이 없거나 만료되면** 쿠폰 단계를 건너뛰고 `coupon_price`를 NULL로 둔다. 요약에 `⚠️ 4910 로그인 만료 — ABLY_JWT_TOKEN 갱신 필요`를 띄운다(지금 문구 재사용).
- **찜 동기화**(`liked.js`)
  - `member_price`를 `/api/v2/goods` 회원가에서 **best-coupon 결과**로 바꾼다. 찜 상품은 수가 적어 상품마다 직접 조회한다.
  - 열 이름은 그대로 두되, 2026-10-11 이전 값은 에이블리 앱 기준이라는 점을 README와 코드 주석에 남긴다.

### 5. 대시보드 — `src/visualizer.js`, `src/dashboard.template.html`
- 지금은 `4910-all.js` 하나(15.9k건에 4.4MB)다. 192k건이면 약 50MB가 되므로 **브랜드별 파일로 나눈다.**
  - `4910/index.js` → `window.__CLOT_4910_INDEX__ = { v: 2, lastScan, brands: [[sno, name, count], ...] }`
  - `4910/b{sno}.js` → 지금 `buildScan4910Payload`와 같은 형식을 브랜드 하나로 잘라 `window.__CLOT_4910_B__[sno] = …`에 담는다. 카드에 `cp`(쿠폰가)를 추가한다.
- `4910 전체` 칩을 누르면 index를 불러와 브랜드 칩 목록을 그린다(판매글 수 내림차순). 브랜드를 고르면 그 파일만 `<script>`로 삽입한다. 기존 file:// 호환 방식이다.
- 정렬에 `쿠폰가 낮은순`과 `쿠폰 할인율순`을 추가한다.
- 나이키(통과 약 5.3만 건, 약 15MB)처럼 큰 브랜드는 카테고리별로 한 번 더 나눌지 구현 계획에서 정한다. **[default: 나누지 않음, 120장씩 점진 렌더링만]**

### 6. 저장소 — `scripts/4910-db.js` (신규), workflow
- Release 태그는 `data-4910`(prerelease, 내용 설명만)이다. 첨부 파일은 다음 두 개다.
  - `4910.db.gz`: 최신본
  - `4910.db.prev.gz`: 직전본, 롤백용
- `pull`
  - `gh release download data-4910 -p 4910.db.gz`로 받아 압축을 푼다.
  - 첨부 파일이 없으면 **처음 한 번만** 저장소의 `data/4910.db`(git에 남은 마지막 커밋본)로 시작한다.
- `push`
  - WAL을 체크포인트한 뒤 `VACUUM`하고 gzip으로 압축한다.
  - 올라가 있던 최신본은 `prev`로 이름을 바꿔 올리고, 새 파일을 `--clobber`로 올린다.
- `4910.yml`
  - `permissions: contents: write`(Release 쓰기)
  - `concurrency: group: clot-4910`
  - `timeout-minutes: 45`
  - secrets: `ABLY_JWT_TOKEN`, `TELEGRAM_*`
- `pages.yml`
  - 빌드 전에 `node scripts/4910-db.js pull`을 실행한다. 실패하면 4910 섹션 없이 빌드한다(지금의 격리 원칙).
  - `workflow_run` 트리거에 `4910 tracker`를 추가한다.
  - `push` paths에서 `data/4910.db`를 뺀다.
- 전환
  - 첫 실행이 Release에 올라간 뒤 `data/4910.db`를 `git rm`하고 `.gitignore`에 추가한다. 기존 이력은 git history에 남는다.
  - `daily`의 4910 단계를 제거한다.

### 7. 규모 대비
- 매일 `SELECT * FROM goods`로 전체를 메모리에 올리는 방식은 309k행이면 수백 MB가 된다. 그래서 `applyScan`을 **브랜드 단위**로 처리한다(`WHERE brand_sno = ?`).
- `price_changes` 인덱스는 그대로 쓴다. `goods`에 `(market_sno)` 인덱스를 추가한다.
- probe 모드: 랭킹 1페이지, 셀러 1곳, 쿠폰함 1회, best-coupon 1회로 도달성을 확인한다.
