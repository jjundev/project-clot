## 성능 실측

동일 로컬 DB·기기·1440×1000, 새 browser context 각 3회, CPU/네트워크 제한 없는 **비압축 로컬 HTTP** 비교다. 검색 준비에는 debounce가 포함된 실제 비기본 검색 완료를 사용했다. 백그라운드 부하와 네트워크에 따라 값이 달라진다.

## 설계상 판단과 한계

- 작은 상품 이력은 같은 파일에 묶되 원문 256KiB 상한과 상품별 날짜 참조·키 필터를 유지했다. 오판 시 다른 상품 이력 혼입 위험이 있어 전체 이력/가격 검증으로 확인했다.
- legacy export helper는 호환을 유지했다. 운영 빌드는 리뷰 후 별도 iterator sink로 분리했으며 가격 이력 `.all()` 호출을 금지하는 회귀를 추가했다. legacy helper를 직접 부르는 외부 코드는 예전 메모리 비용을 가질 수 있다.
- 직렬화된 HTML/runtime의 연결 때문에 Task 3·4 작업이 일부 겹쳤다. 각각의 데이터·전송·브라우저 검증은 별도로 유지했다. 인터페이스 결합의 비용은 전체 재검증으로 확인했다.
- 360개 상태에서 카드가 포커스를 가지고 있으면 추가 페이지 적용을 보류해 포커스와 DOM 상한을 함께 보존한다. 다음 로딩은 포커스가 목록 밖으로 이동하면 가능하다.
- 전체 인덱스의 다운로드·검색·Worker 메모리는 **상품 수에 비례**한다. 무한한 상품 수 확장을 보장하지 않는다. 이력 누적을 초기 화면과 분리한 개선이다.
- 16MiB는 성공한 이력 파일의 **원문 캐시** 한도다. 표시 중인 이력, 진행 중 요청, 카드와 인덱스, JS heap 전체의 상한이 아니다. 전체 기간을 선택한 한 상품의 상세 처리 비용은 그 상품의 이력 길이에 비례한다.
- 기존 일일 수집·DIRECT/ESTIMATED 판정·회원 조회 한도·원본 DB 이력을 유지했다. 관련 없는 `data/4910-all.js`도 SHA256 동일하게 보존했다.
