# 상품 로딩 속도 개선 전후 측정

측정일: 2026-10-26. 대상: `worktree-dashboard-loading-speed` 브랜치(설계 `docs/superpowers/specs/2026-10-26-dashboard-loading-speed.md`).

## 방법

- 측정 스크립트: `node scripts/measure-dashboard-loading.js <url> <out.json>`. 시나리오별 3회, Chrome headless, 1440×1000, 네트워크·CPU 무제한이다. 표의 값은 3회의 중앙값이다.
- `첫 카드`: 화면에 `.card`가 처음 나온 시각이다. `건수 확정`(`countReadyMs`): 검색어 입력 전 `#shownN`이 처음 숫자가 된 시각이다. `검색 완료`: 그 뒤 일치 없는 검색어를 입력해 `0`이 확정된 시각이고, 180ms 입력 지연을 포함한다.
- 인덱스 파일 수와 압축 바이트는 Worker가 받은 `assets/index-*` 응답을 센 값이다.
- 로컬 비교: Pages 워크플로와 같은 명령으로 빌드했다(`4910-db pull`, `musinsa-db pull`, `CLOT_REQUIRE_MUSINSA_WIDE=1 … visualize --no-open`). main(`fe42cd1`)과 브랜치를 같은 DB 파일로 빌드했다. 빌드 결과는 둘 다 505,853개 상품이며, 브랜치 빌드는 `verify-dashboard-build.js` 검사를 통과했다. 로컬 서버는 gzip을 쓰는 HTTP/1.1이다. Pages(HTTP/2)와 연결 조건이 다르므로 절대 시간은 참고치다. 특히 HTTP/1.1에서는 Chrome이 호스트당 동시 연결을 6개로 제한해 동시 8개 효과가 드러나지 않는다.

## 해석

- 전체·전체 기본 화면은 건수와 카드가 인덱스 응답과 관계없이 첫 카드 시점에 확정된다. 검색에 필요한 인덱스는 live tier만 받으므로 파일 수는 60%, 바이트는 69% 줄었다.
- 무신사·상의는 무신사 상품 대부분이 48시간 안에 확인되지 않은 history 행이어서 받는 live 파일이 1개뿐이다. 현재 데이터의 특성이며, 무신사 수집 주기가 바뀌면 live 비중도 달라진다.
- 과거 기록 포함은 이번 설계로 빨라지지 않는다. tier 분할로 파일이 1,006개에서 1,046개로 늘었고 로컬 건수 확정은 3.52초에서 3.84초로 약 9% 느려졌다. 저장된 조건이 기본이 아니면 미리보기 카드 대신 스켈레톤을 보여주므로(N1) 첫 카드도 결과가 확정될 때 나온다. 개선 전 0.10초 첫 카드는 조건과 다른 기본 상품 미리보기였다.
- 실사이트에서 전체·전체 기본의 건수 확정은 14.12초에서 0.13초로, 검색 완료는 14.44초에서 1.50초로 줄었다. 무신사·상의는 건수 확정이 1.63초에서 0.19초로 줄었다.
