JS heap 값은 해당 시점 Chrome의 관측값이며 GC 이후 잔존 메모리나 브라우저 전체 RAM 사용량과 같지 않다. 응답 크기는 이번 응답의 Resource Timing 기준이다. 과거 측정과 압축/전송 조건이 같다고 전제하지 않는다.

로컬 전체 빌드 산출물은 이전 4910 DB라 439,729개로 공개 사이트보다 94개 적다. 이 산출물의 요약 원문 합계는 371,925,246 bytes이며 개별 gzip 합계는 38,621,365 bytes다. 무신사 이력 파일 전체는 36,994,076 bytes, 가장 큰 이력 묶음은 335,668 bytes다. 공개 사이트 수치와 혼합하지 않는다.

로컬 원본 모델 함수에 전체 439,729개를 넣고 세 번씩 측정한 순수 조회/정렬 시간:

Node 함수 측정이므로 브라우저 INP로 해석하지 않는다. 공개 브라우저 검색 입력에서 결과 확인까지는 약 225–407ms였으나 180ms debounce와 측정용 대기를 포함하므로 입력 지연의 정확한 분해값은 아니다.

## 확인된 병목과 누적 영향

1. `src/dashboard-runtime.js:13`부터 모든 요약 파일을 네 개씩 요청하고 전부 검증한 뒤 ready로 전환한다. `src/dashboard.template.html:875`는 그때까지 상품 목록을 숨긴다. 처음 120개를 보기 위해 전체 요약을 받아야 한다.
2. 요약에는 카드 필드 외에 검색 문자열, 정규화 브랜드, 반복 URL·라벨·속성명이 중복된다. 이력은 분리했지만 요약 자체도 약 372MB 원문이다.
3. `src/dashboard-model.js`의 `queryCatalog`가 매번 전체 순회·정렬한다. 메인 스레드에서 실행되고, 브랜드 선택창이 닫혀 있어도 `renderBrandBar`가 전체 상품으로 브랜드 Map을 만든다.
4. 무신사 상세는 최대 2,000개 상품의 전체 이력을 한 파일로 받는다. 4910은 브랜드 단위 전체 이력을 받는다. `src/dashboard-runtime.js:4`의 캐시는 성공한 파일을 계속 보관하며 상한/퇴출이 없다.
5. `src/dashboard-musinsa.js:16`에서 빌드가 ACTIVE 전체 가격 이력을 한꺼번에 메모리로 읽는다. 장기간 이력 누적은 방문자 상세 로딩과 Actions 빌드 메모리/시간에도 영향을 줄 수 있다.
6. 카드 DOM은 120개씩 추가하지만 스크롤에 따라 계속 쌓인다. 현재 첫 로딩의 주원인은 전체 요약 다운로드이며 DOM 가상화만으로 해결되지 않는다.

매일 기존 30만 상품을 재조사한다고 상품 요약이 매일 30만 행씩 증가하는 것은 아니다. 상품 수가 그대로면 가격 이력 증가가 첫 요약 전송량을 직접 선형 증가시키지는 않는다. 다만 현재 첫 로딩이 이미 무겁고, 새 상품 증가와 상세 이력 누적에 대한 방어가 부족하다.
