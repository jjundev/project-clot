## 결론

**카테고리를 분할하면 고유 30만 상품을 실제로 확보할 수 있다.** 공식 5개 대분류 아래의 2단계 분류 59개를 나눠 조회해 고유 **300,086개**를 얻었다. API 가능성은 확인했지만 **현재 코드에서 수집 개수만 늘려 운영하는 안은 진행 불가**다. 쿠폰 목록 60페이지 제한과 분류 저장 방식, 시간 예산을 함께 수정해야 한다.

대형 쿠폰 `353190`의 전체 목록에서 이 조사대상과 일치한 상품은 211,731개였고, 기존 60페이지 제한만 재현하면 그중 **123,063개가 목록에서 빠진다.** 이는 목록 매핑 누락의 실측이며, 회원 직접 조회로 보완되는 경우가 있으므로 잘못된 최종 가격 개수와 같다고 해석하면 안 된다.

## 대형 쿠폰 전체 목록과 조사대상의 교집합

- **1,733회·394.206초**, 작업자 3개, 작업자별 다음 요청 전 500ms 대기, HTTP 상태 `{'200': 1733}`. 서버가 반환한 마지막 페이지의 `hasNext=false`를 확인했다.

## 소형 쿠폰과 세부 분류 인자

최근 번호순 USABLE 쿠폰 24종을 조회했다. 이 표본은 무작위 표본이 아니다. 그중 상품 수가 1~3,000개인 **15종**은 1~2페이지로 실제 끝까지 읽었으며, 모두 고유 상품 수가 표시 개수와 일치했고 마지막 `hasNext=false`였다. 예: `360260` 594개, `359959` 355개, `359712` 318개. 0개인 쿠폰은 비어 있다는 결과와 구분해 기록했다.

쿠폰 API의 세부 분류 인자도 `001001`, `001002`, `001004`, `103004`, `004003`에서 첫 페이지·개수·다음 페이지 존재를 확인했다. **이 세부 분류 쿠폰 목록은 완주하지 않았다.** 위 교집합 증명은 대분류별 완주 결과를 사용한다.

## 현재 등록 쿠폰 전체의 호출량 개수 조사

- 최초 backfill Actions [38754493805](https://github.com/jjundev/project-clot/actions/runs/38754493805)는 정상 종료했다. Release DB `musinsa-wide.db.gz`의 2026-10-15 스냅샷을 `/tmp`에 받아 읽기 전용으로 확인했다.
- 스냅샷의 USABLE은 1,158종, 그중 2026-10-16 기준 미만료는 **1,154종**이다. 현재 `usableCoupons(date)`와 같은 만료 조건이다. 오늘 새 회원 조회로 재분류한 개수는 아니다.
- 이 **1,154종 모두**에 합산 5개 대분류의 익명 count API를 호출했다. 요청 1,154회, HTTP 상태 `{'200': 1154}`, **329.012초**, 작업자 2개·500ms 대기, 재시도 없음.
- 상품 수 합계 **2,912,012건**은 쿠폰 간 중복을 포함한다. 고유 상품 수가 아니다.
- 3,000개 이하 1,134종(0개 7종 포함), 3,000개 초과 20종이었다.
- 전체 합산 목록을 끝까지 읽는 산술적 페이지 비용은 `Σ max(1, ceil(count/300)) = 10,462회`다. 현재 방식처럼 큰 쿠폰을 대분류별로 나눠 읽으면, 대분류의 개수가 합산 개수로 분할된다는 조건에서 **약 10,482~10,562회**다. 하한은 큰 쿠폰마다 합산 첫 페이지 1회를, 상한은 여기에 대분류 반올림·빈 분류 첫 페이지 차이 최대 4회를 더한 값이다. 5개 대분류가 combined과 같은 서로 겹치지 않는 분할이고 개수가 고정됐다는 조건이다. 종료 이후 확인 요청·재시도는 제외한다.
- 이는 **현재 개수에 근거한 전체 범위 순회 비용 계산**이다. 전 쿠폰 실제 완주 호출량, 30만 대상에 맞춘 floor 중단 후 호출량, 실패·재시도·새 쿠폰 탐색 호출량은 아니다. count와 list 사이의 변동·분류 차이도 발생할 수 있다.
- 대형 쿠폰의 실측 처리율을 현재 운영 목록 병렬도 2에 단순 적용하면 목록 전체 순회만 대략 1시간 규모다. 이는 로컬 추산이며, 실제 일일 작업 시간이나 GitHub Actions 성능을 검증한 수치가 아니다. 분할 상품 수집·DB 처리·압축·업로드 시간은 별도로 필요하다.

backfill 스냅샷은 `backfill_done=2026-10-15`, `coupon_goods=0행`이다. backfill은 번호 등록·판별을 하고 목록 매핑은 다음 일상 실행에 맡기므로, backfill 완료와 전체 쿠폰 매핑 완료를 혼동하면 안 된다.

## 검증된 구현 전제와 금지할 가정

분할 조회의 30만 접근성과 대형 쿠폰의 깊은 목록 제공은 구현 검토에 사용할 수 있다. 조회용 세부 분류를 DB `cat`에 그대로 넣으면 대분류 floor 조회와 미노출 집계 의미가 바뀐다. 기존 60페이지 제한의 결과를 전체 목록이라고 간주하거나, 이 대표 쿠폰의 성공을 전 쿠폰 가격 정확도 보장으로 확대해서는 안 된다.

## 필요한 후속 작업

1. 조회 분할과 영속 대분류·미노출 집계의 관계를 정하고, 쿠폰 목록 잘림을 명시적으로 처리한다.
2. 확대 범위에 맞는 단계별 시간 예산을 정한 뒤 전 쿠폰 목록·가격 표본·DB 비용을 포함한 통합 실행으로 확인한다.
3. Actions 환경에서 실행 시간·429·목록 완료율·가격 정확도를 확인하고 운영 범위를 확정한다.
