# 무신사 쿠폰→상품 목록 검증 (쿠폰가 계산을 뒤집는 설계의 숨은 가정)

상품마다 회원 쿠폰을 묻는 대신, 쿠폰마다 적용 상품 목록(`api2/coupon/plp/v1/goods`)을 받아 3만 개 전부의 쿠폰가를 매일 계산하는 설계가 있다. 이 문서는 그 설계가 기대는 가정을 하나씩 확인한다.

- 1차 검증(H1~H16): 목록 자체를 확인했다. 목록은 정확하다. 남은 문제는 쿠폰 번호를 아는 방법(쿠폰 발견)이었다.
- 2차 검증(H17~H23): 쿠폰 발견을 확인했다. 쿠폰 번호를 차례로 훑는 방법(번호 순회)으로 풀린다.

재현:
- 1차: `node scripts/musinsa-coupon-plp-verify.js probe | scan | sample --db <db> | walk --db <db> | evaluate --db <db>`.
- 2차 순서:
  1. `enum-count`
  2. `enum-check --db <db>`
  3. 날짜가 바뀐 뒤 `enum-retest --from 359900`
  4. `enum-expiry --db <db>`
  5. `enum-evaluate --db <db> --date 2026-10-14`
- 결과는 `logs/plp-verify/*.json`(gitignored)에 남는다.
- 2차의 출처:
  - 원래 실행은 같은 요청을 보내는 임시 스크립트로 했다. 그 결과 파일을 위 명령의 형식으로 옮겼고, `enum-evaluate`가 그 파일로 이 문서의 숫자를 그대로 다시 낸다.
  - 네트워크를 쓰는 명령은 작은 범위로 다시 돌려 동작을 확인했다(회원 조회 3건).
  - H21의 00:00:57 관찰(`enum-expiry.json`)은 임시 스크립트의 출력을 옮겨 적은 것이다. 00:24 관찰(`enum-expiry-2.json`)은 `enum-expiry`로 잰 것이다.

실행:
- 1차: 2026-10-14 22:05–22:30 KST.
- 2차: 2026-10-14 23:43 – 10-15 00:25 KST.
- 둘 다 로컬 IP에서 실행했다. DB는 같은 날 init 결과다(Release `data-musinsa`, 쿠폰 조회 4,000개, 20:00경).

요청 수 (모두 HTTP 200, 429와 재시도는 0건):

| 차수 | 회원 쿠키 | 비로그인 API |
|---|---|---|
| 1차 | 506건 (새 표본 500 + 비교 6) | 약 1,720건 (목록 스캔 500, 쿠폰 목록 1,182, 확인용 약 40) |
| 2차 | 175건 (판별 114 + 재판별 58 + 스크립트 점검 3), 쿠키를 붙인 쿠폰 목록 4건 | 2,616건 (번호 count 2,098, 쿠폰 목록 518: 대부분 첫 페이지) |

## H1·H2: 목록과 회원 조회의 일치

"쌍"은 (상품, 그 상품에 회원 조회가 돌려준 쿠폰)이다.

| 모집단 | 보유 쌍 | 목록에도 있음 | 회원 조회에만 있음 | 목록에만 있음 |
|---|---|---|---|---|
| init에서 조회한 4,000개 (10-14 범위 안) | 16,219 | 16,216 | 3 | 0 |
| 새 무작위 표본 500개 | 2,370 | 2,369 | 1 | 0 |

- 모집단: 아직 조회하지 않은 상품 중 대분류마다 100개를 무작위로 골랐다. 10-14 스캔에서 품절이 아닌 상품만 썼다.
- 목록에만 있는 쌍이 0이다. 목록으로 계산하면 쿠폰을 **더 주는** 쪽으로 틀리는 일은 없었다.
- 누락 4쌍은 모두 브랜드 정기 쿠폰에서 나왔다.
  - `354094` 10월 이달의 미즈노 6%: 목록 전체 36개가 5개 대분류 밖의 상품이다. 조회로 이 쿠폰을 받은 신발(4982686)은 목록에 없다.
  - `355780` 10월 이달의 토앤토 6%: 목록이 대분류 필터 없이도 0건이다.
  - `355216` 10월 이달의 밸롭 6%: 목록 373개에 신발 2개(1798200, 1798273)가 빠져 있다.
- 따라서 목록만 믿으면 안 된다. 회원 조회로 직접 확인한 상품은 그 결과를 함께 써야 한다.

## H3·H5·H7: API 동작

- `couponKind=CART`는 모든 쿠폰에서 0건이다. 상품 페이지의 "적용 상품" 링크가 이 값을 쓴다. `PRODUCT`만 목록을 준다. 그 밖의 값은 400이다.
- 로그인 여부와 무관하다(4종):

  | 쿠폰 | 비로그인 개수 | 회원 개수 |
  |---|---|---|
  | 359200 | 4,127 | 4,127 |
  | 353190 | 516,253 | 516,253 |
  | 359700 | 414 | 414 |
  | 326028 | 125 | 125 |

  첫 페이지의 상품과 순서도 같았다.
- 깊은 페이지에 상한이 없다. 200개 단위로 대분류 001의 500페이지(10만 번째), 필터 없이 4,000페이지(80만 번째)까지 정상 응답했다.
- 페이지 크기는 200, 201, 300이 동작한다. 301, 320, 350, 400, 450, 499, 500은 모두 빈 목록이다. **오류가 아니라 빈 성공 응답**이므로 구현에서 반드시 막아야 한다.

## H4: 최소금액

최소금액(`lowPrice`)이 있는 쿠폰 94종의 목록 상품 75,317개 중 가격이 최소금액 미만인 상품은 0개다. 목록은 회원 조회와 같은 기준으로 이미 걸러 준다. 그러므로 가격이 최소금액을 넘나드는 상품은 그날의 목록을 따라야 한다.

## H6: 정렬과 범위 경계

- `sortCode=REVIEW`는 화면에 보이는 리뷰 수와 정확히 같은 순서가 아니다.
  - 카테고리 목록에서 리뷰 수가 바로 앞 상품보다 큰 경우가 6,722건 있었다. 앞선 상품과의 비율은 최대 1.36배였다.
  - 쿠폰 목록도 마찬가지다(28,237건).
  - 정렬 기준은 캐시된 리뷰 수로 보인다.
- 그래도 두 목록의 순서는 서로 같다. 쿠폰 목록 안에서 이웃한 범위 안 상품 130,347쌍 중 카테고리 순위가 거꾸로인 쌍은 110(0.08%)이다. 리뷰 수가 같아 순서만 바뀐 쌍은 238이다.
- 멈춤 규칙: "페이지 마지막 상품의 리뷰 수 < 그 대분류 범위의 최저 리뷰 수"이면 멈춘다.
  - 10-14 경계값: 001 199, 002 45, 003 113, 103 22, 004 18.
  - 범위 안 상품은 모두 경계 이상이다. 따라서 경계 미만인 상품은 범위 밖이고, 순서가 같으므로 그 뒤도 모두 범위 밖이다.
  - 대분류별 순회 120회 중 경계에서 멈춤 86, 목록 끝 34였다. 이 멈춤 때문에 놓친 보유 쌍은 0이다.
  - 스캔과 순회 사이의 시간차를 감안해 구현에서는 한 페이지 더 읽는 여유를 두는 편이 안전하다.

## H8: 호출량과 시간

- 순회 결과: 쿠폰 396종(init 240 + 표본에서 새로 본 156), 1,182회, 378초. 2개 병렬, 호출 사이 0.5초, 모두 200.
- 5개 대분류 안의 상품이 3,000개 이하인 쿠폰은 목록 전체를 한 번에 읽었다. 372종, 679페이지(쿠폰당 1.83페이지).
- 3,000개를 넘는 쿠폰은 대분류마다 범위 경계까지 읽었다. 24종, 503페이지.
  - 회원 정기 쿠폰 4종(실버 2~5%): 각 77페이지.
  - 깜짝 쿠폰 5%: 71페이지.
  - 정기 쿠폰 4종은 대상 수가 조금씩 달라(516,248~520,360개) 각각 읽어야 한다.
- 쿠폰 종류 추정: 관찰 396종, 상품 1개에서만 본 쿠폰 169종, 2개에서 본 쿠폰 56종이다. Chao1 추정은 약 651종이다. 표본이 오래된 상품 쪽으로 치우쳐 있어 실제로는 더 많을 수 있다.
- 하루 예상 호출: 503 + 1.83 × (쿠폰 수 − 24).
  - 650종이면 약 1,650회, 1,000종이면 약 2,300회.
  - 측정 속도(초당 3.1회)로 9~12분이다.

## H9: 쿠폰 조건

- 396종 모두 상품이 달라도 율, 상한, 최소금액, 만료일이 같다. 한 상품에서 배운 조건을 목록의 모든 상품에 적용해도 된다.
- 정률이 아닌 쿠폰은 1종(`359146` 슈펜 삭형 쿠폰)이다. 표본 2,492건은 모두 `%`/`P`였다.
- 표본 500개에서 API가 준 최대 할인액과 로컬 식(`couponDiscountMusinsa`)이 500/500 일치했다.

## H10·H12: 쿠폰 발견 (틀린 가정)

목록으로 계산하려면 회원이 쓸 수 있는 쿠폰 번호를 먼저 알아야 하고, 이것은 회원 조회로만 알 수 있다. 새 표본 500개의 최대 쿠폰 할인액을 "아는 쿠폰 + 쿠폰별 목록"으로 맞힌 비율은 다음과 같다.

| 쿠폰을 찾은 곳 | 정확 |
|---|---|
| init 4,000개 (240종) | 82.2% (411/500) |
| init 중 무작위 2,000개 | 80.8~82.0% |
| init 중 무작위 1,000개 | 78.4~79.2% |
| init 중 무작위 500개 | 76.2~77.8% |
| init 4,000개 + 표본의 다른 상품 499개 | 89.4% |
| 넓은 쿠폰 21종 + 같은 브랜드 다른 상품 1개 | 88.2% (320/363) |
| 넓은 쿠폰 21종 + 같은 브랜드 다른 상품 2개 | 92.1% (256/278) |
| 넓은 쿠폰 21종 + 같은 브랜드 다른 상품 3개 | 93.6% (234/250) |

- 이전 답변의 "무작위 1,000개 → 97%"는 같은 4,000개 안에서 찾고 맞힌 결과라 부풀려진 값이다.
- init 4,000개는 상품번호가 가장 작은 상품이라 브랜드가 488개뿐이다(전체 1,803개). 쿠폰은 브랜드 정기 쿠폰("10월 이달의 ○○ 6%")과 행사 쿠폰(SG)이 많다. 표본 브랜드 285개 중 118개에 브랜드 쿠폰이 있었다.
- 놓친 89건은 모두 "모르는 쿠폰" 때문이다(SB 56, SG 33). 목록 누락, 조건 차이, 과대 예측은 0이다. **틀릴 때는 항상 실제보다 비싸게 보인다.**
- 브랜드 단위 시뮬레이션은 같은 브랜드의 조회 상품이 있는 표본(363/500)에만 해당한다.

## H17~H23: 쿠폰 번호 순회 (2차 검증)

H10과 H12는 "쿠폰 번호는 회원 조회로만 알 수 있다"는 전제에서 나왔다. 2차 검증에서 이 전제를 다시 확인했다.
- 쿠폰 번호는 연속된 정수다.
- count API는 쿠키 없이 아무 번호에나 답한다.
- 그러므로 번호를 차례로 물으면 쿠폰을 빠짐없이 찾을 수 있다.

### H17: count API로 번호 훑기

```
GET https://api.musinsa.com/api2/coupon/plp/v1/goods/count
    ?couponNo=<n>&couponKind=PRODUCT&caller=COUPON&gf=A&category=001,002,003,103,004
→ {"meta":{"result":"SUCCESS","errorCode":null,"message":null},"data":4127}
```

없는 번호(99,999,999)는 `data: 0`이다.

네 구간의 번호 1,744개를 조회했다. 2개 병렬, 호출 사이 0.5초로 482초가 걸렸고 모두 200이었다.

### H18: 번호를 훑으면 쿠폰을 놓치지 않는다

- 구간 안의 아는 쿠폰 16종은 모두 count > 0이었다.
- H19의 회원 조회 114회는 쿠폰 167종을 돌려줬다. 그중 구간 안에 있는 24종도 모두 count > 0이었다.
- 따라서 구간 안에서 회원이 쓸 수 있는 쿠폰은 번호 순회로 모두 찾을 수 있다. 남는 일은 그중 우리 계정이 쓸 수 있는 쿠폰을 가려내는 것이다.

- 회원 쿠키를 붙여 쿠폰 목록을 불러도 상품의 `couponPrice`는 null이었다(4종). 목록만으로는 회원 대상 여부를 알 수 없다.

## 설계에 주는 의미

1. **목록 (1차, 검증됨).** 쿠폰→상품 목록으로 아는 쿠폰을 3만 개 전부에 매일 적용할 수 있다. 비로그인이고 정확하다(목록에만 있는 쌍 0).
2. **쿠폰 발견 (2차, 검증됨).** 번호 순회로 쿠폰을 빠짐없이 찾는다. 회원 조회는 찾은 쿠폰 중 우리 계정 쿠폰을 가려내는 데만 쓴다. 하루 약 60회로 추정된다.
3. **정확도.** 계산상 약 99%다(99.6%, 498/500). 남는 오차와 보완 방법:
   - 오래된 번호의 장기 쿠폰: 매일 표본 회원 조회와 이웃 번호 조회로 보완한다.
   - 목록 누락: 직접 조회한 결과를 합쳐서 보완한다.
4. **1차의 결론을 대체한다.** 1차 결론은 "회원 조회 4,000건을 그대로 쓰고 브랜드당 2개로 약 92%"였다. 이제 회원 조회는 하루 약 260회(판별 약 60 + 표본 200)로 줄일 수 있다.
5. **구현 시 처리할 것.**
   - 페이지 크기가 300을 넘으면 빈 응답이 온다(H7).
   - 목록에 없는 쿠폰이 있다(H2). 조회한 상품은 자기 조회 결과와 합쳐서 계산한다.
   - 만료는 회원 조회로 받은 만료일로 판단한다. count는 늦게 빠진다(H21).
   - 판별 결과를 저장한다. 대상 아님인 번호는 다시 판별하지 않는다. 다만 다른 회원 조회에서 그 쿠폰이 나오면 쓸 수 있음으로 바꾼다(H20).
   - 쿠폰을 늦게 찾으면 "가격 하락"처럼 보인다. 요약의 하락 알림에서 구분해야 한다.
   - GitHub Actions IP에서 dry-run으로 H15를 확인해야 한다. 2차 방식은 비로그인 호출이 하루 약 4,000회다.
6. **확인하지 못한 것.**
   - 여러 날에 걸친 쿠폰 생존: 다 쓴 쿠폰, 선착순 소진 쿠폰
   - 만든 뒤 상품이 늦게 붙는 쿠폰
   - Actions IP에서 하루 비로그인 약 4,000회가 괜찮은지
