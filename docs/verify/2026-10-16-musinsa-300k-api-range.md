# 무신사 30만 상품 확대 — API 범위·호출량 검증

검증일: 2026-10-16 KST. 대상 저장소: `project-clot`.

## 결론

**현재 5개 대분류의 페이지 수만 늘려서는 이번 검증에서 고유 상품 30만 개에 도달하지 못했다.** `REVIEW` 정렬의 서버 페이지 체인을 끝까지 읽은 결과, 고유 상품은 **291,342개**였다. 상의·아우터·바지·가방은 표시된 전체 상품 수와 무관하게 1,000페이지에서 `hasNext=false`로 끝났고, 신발은 856페이지에서 실제 목록 끝에 도달했다.

이는 30만 상품 수집 자체가 불가능하다는 뜻은 아니다. 하위 카테고리의 별도 페이지 체인은 확인했지만, 이를 나눠 조회해 중복 제거 후 고유 30만 개를 확보하는 검증은 아직 수행하지 않았다. **현재 대분류의 depth만 올리는 안은 진행 불가이며, 분할 조회 방식은 추가 검증이 필요하다.**

## 검증 방법과 범위

- 로컬 Mac에서 비로그인 GET 요청만 실행했다. 회원 쿠키는 사용하지 않았다.
- 기존 `fetchCategoryGoodsPage`와 무신사 클라이언트를 사용했다.
- 첫 페이지는 공식 카테고리 HTML의 `__NEXT_DATA__`, 이후는 서버가 반환한 `nextPageUrl`을 순서대로 따라갔다.
- 조건은 `gf=A`, `sortCode=REVIEW`, 페이지 크기 60개다.
- 작업자 2개, 작업자별 다음 요청 전 대기 300ms로 실행했다. 상품번호로 대분류 내·전체 중복을 제거했다.
- 프로브의 목표는 고유 300,000개, 대분류별 최대 1,400페이지였지만, 모든 체인이 그 전에 종료됐다. 코드의 인위적인 페이지 제한으로 종료된 결과가 아니다.
- 운영 코드·설정·DB·Release는 변경하지 않았다. 진행 중인 최초 backfill과 별개인 로컬 임시 프로세스에서 측정했다.

각 대분류를 시작한 시점이 다르며, 표시된 상품 수는 수집 중에도 변할 수 있다. 첫 사전 조회의 합계와 위 체인 시작 시점의 합계가 조금 다르다. 표시 전체 상품 수를 실제 접근 가능한 수나 특정 시점의 고정된 모집단으로 간주하면 안 된다.

- 실제 순차 조회 요청: **4,856회**, 전부 **HTTP 200**. 이 체인 조회에서 403·429·재시도는 없었다.
- 유효 상품 항목: 291,351개. 상의 2개·아우터 7개의 중복을 제거해 고유 상품 291,342개를 얻었다. 이번 수집에서는 대분류 간 추가 중복은 없었다.
- 경과 시간: **1,156.107초 = 약 19분 16초**. 상품 목록 조회·파싱·중복 제거와 진단 기록까지의 시간이다.
- 응답 본문: 253,946,411바이트, 약 254MB. `fetch`로 읽은 압축 해제 후 본문 크기이며 실제 회선 전송량은 측정하지 않았다.
- 운영 DB 반영, 쿠폰 목록 전체 순회, 가격 계산, 압축·Release 업로드 시간은 포함하지 않았다.

## 페이지 이동 제약

1. 서버가 준 2페이지 URL의 `hmacId`는 유지하고 `page`만 1,000으로 바꾸면 **HTTP 403**이었다. 이 요청은 위 정상 순차 조회 4,856회와 별도의 진단 요청이다.
2. 공식 카테고리 HTML URL에 `page=200` 또는 `page=1000`을 붙여도 실제 반환 데이터는 1페이지였고, 다음 주소도 2페이지였다.
3. 따라서 페이지 번호를 임의 수정해 깊은 페이지로 건너뛸 수 있다고 가정하면 안 된다. 현재 확인된 경로에서는 서명된 `nextPageUrl`을 따라가야 한다.

## 쿠폰 적용 상품 API

상품 카테고리 목록과 쿠폰 적용 상품 목록은 서로 다른 API다. 상품 목록에서 관찰한 1,000페이지 제한을 쿠폰 API에도 적용하면 안 된다.

- 쿠폰 번호 `353190`을 비로그인으로 조회했다. 이 쿠폰을 현재 계정이 사용할 수 있는지는 이번 검증에서 확인하지 않았다.
- 대분류별 60·61·200·201페이지를 조회했다. 상품이 남은 구간에서는 61페이지 이후에도 정상 응답했고, 목록 끝을 넘은 구간은 빈 목록과 `hasNext=false`를 반환했다.
- 5개 대분류 합산 목록은 **1,000페이지에서 300개·`hasNext=true`**, **1,730페이지에서 250개·`hasNext=false`**였다. 이때 표시 합계는 518,950개였다.
- 앞선 대분류별 조회의 개수 합은 518,961개였다. 그 시점의 개수로 각 대분류를 전부 읽는 비용은 `1 + Σ ceil(대분류 개수 / 300) = 1,733회`다. 앞의 1회는 현재 알고리즘의 합산 첫 페이지다. 이는 **쿠폰 한 종을 5개 대분류 전체 범위에서 읽는 예시 비용**이며, 고유 30만 대상의 예상 일일 비용이나 전체 쿠폰 비용은 아니다.

검증 당시 구현의 `MAX_PAGES_PER_CAT=60`은 API 한도가 아니라 코드 한도다. 큰 쿠폰은 대분류당 최대 18,000개까지만 읽고도 정상 완료로 처리한다. 이 상태로 조사 범위만 확대하면 깊은 순위의 상품에서 적용 쿠폰을 놓칠 수 있다.

## 호출량과 실행 시간 판단

- 상품 목록 30만 항목의 산술적 최소 비용은 `300,000 / 60 = 5,000회`다. 고유 30만 개를 확보하려면 중복·비상품 항목·짧은 페이지만큼 더 필요할 수 있다.
- 회원 쿠폰 조회 상한은 상품 수에 비례해 늘릴 필요가 없지만, 쿠폰 적용 목록의 비로그인 호출량은 증가할 수 있다. **30만 범위의 전체 쿠폰 호출량과 가격 정확도는 아직 측정하지 않았다.**
- 이번 로컬 4,856회 무차단 결과는 GitHub Actions IP 또는 반복 일일 운영의 무차단 보장이 아니다.
- 검증 당시 기본 상품 수집은 100페이지, CLI `--depth` 허용 상한도 100이었다.
- 내부 시간 예산은 상품 수집 20분, 번호 순회 12분, 판별 15분, 전체 네트워크 단계 35분이다. 이 값들은 모두 실행 시작 기준이므로, 상품 수집이 길어지면 번호 순회·판별 시간이 먼저 소진될 수 있다.
- 현재 Actions 일상 작업 제한은 45분이라는 설정값이다. GitHub 공식 문서의 호스팅 작업 실행 한도는 **6시간**이다. 2026-10-16 KST에 [GitHub Actions limits](https://docs.github.com/en/actions/reference/limits)를 확인했다. 시간 제한만 늘려서는 페이지 범위·쿠폰 목록 누락 문제를 해결할 수 없다.
