# 가격 대시보드 로딩 개선 제안

2026-10-16 KST. 상태: 사용자 승인 후 구현·테스트·배포·공개 사이트 확인 완료.

사용자는 grill-yourself 설계의 권장 B안과 최근 90일 기본 표시, 전체 기간 선택 조회를 승인했고 구현·테스트·재배포·실제 사이트 확인·최종 결과 Markdown 저장을 요청했다.

## 목적과 유지할 기능

사용자는 이력이 누적되어도 사이트를 빠르게 열고 전체 상품을 검색할 수 있기를 요청했다. GitHub Pages 정적 호스팅, 기존 카드·검색·정렬·필터·브랜드 다중 선택·상품 직접 링크를 유지한다. DIRECT/ESTIMATED/출처 미확인, 기준일, 쿠폰 예외 경고와 정확한 집계도 유지한다. 수집 DB의 과거 기록은 삭제하지 않는다.

현재 병목은 첫 목록 표시 전에 221개 요약 파일을 전부 받는 방식이다. 단일 공개 측정에서 14.65초, 요약 응답 본문 39.16MB가 관측됐다. 점검 결과와 한계는 `docs/verify/2026-10-16-dashboard-loading-audit.md`를 따른다.

## 제안하는 범위

### 1. 첫 화면을 전체 다운로드와 분리

빌드 시 기본 정렬의 첫 120개 카드와 그 조건의 정확한 집계를 생성해 HTML에 포함한다. 새 방문자는 전체 검색 인덱스 다운로드를 기다리지 않고 첫 상품을 본다. 저장된 출처/카테고리/정렬이 기본과 다르면 기본 결과를 해당 조건 결과로 가장하지 않는다. 해당 조건의 계산이 끝날 때까지 로딩 상태를 표시한다. 쿠폰 예외와 기준일은 초기 HTML에서 바로 보인다.

기존 찜/기본 상품의 `inlineHistories`도 HTML에서 분리한다. 무신사 wide뿐 아니라 기존 무신사 찜과 4910 찜까지 같은 이력 분할/캐시 정책을 적용한다. 최초 HTML에 이력 행을 숨겨 넣지 않고, 초기 데이터 크기를 이력 행 수와 독립적으로 검증한다.

### 2. 요약을 검색 인덱스와 카드 데이터로 분리

전체 검색에 필요한 상품 식별, 이름/브랜드 검색값, 가격·정렬·필터 필드와 카드 참조만 경량 인덱스로 직렬화한다. 반복 키·출처·라벨은 코드/사전으로 표현한다. 이미지 URL, 상품 URL, 상세 참조 등은 조회한 페이지의 카드 데이터에서 읽는다. 원본 요약과 새 인덱스의 전체 집계·순서·가격·출처가 같음을 빌드 검증기로 확인한다.

인덱스는 과거 이력 길이에 비례해 커지지 않아야 한다. 신규 상품 수에 따른 증가는 남으므로 무한 확장을 보장한다고 주장하지 않는다.

### 3. 전체 조회를 화면 처리와 분리

HTTP 사이트는 Web Worker에서 인덱스를 읽고 검색·정렬·집계를 수행한다. 메인 스레드는 현재 페이지 카드와 집계만 받는다. 이전 요청의 늦은 응답이 새 검색을 덮어쓰지 않도록 요청 번호를 검증한다. 전체 인덱스가 준비되기 전에는 비기본 검색 결과/숫자를 부분 집계로 표시하지 않는다. Worker/데이터 실패에는 재시도 수단을 제공한다.

현재 메인 스레드의 전체 `getCatalog().items` 접근을 비동기 계약으로 교체한다. 조회 응답은 요청 번호, 결과 집합 식별자, 정확한 facets와 총수, 현재 페이지 카드, 다음 페이지 위치를 포함한다. 상품 키 조회는 현재 페이지 밖의 직접 링크도 찾는다. 상세의 이전/다음 이동은 해당 결과 집합과 위치를 기준으로 아직 받지 않은 카드 페이지를 요청하며 현재 검색 순서를 보존한다. 브랜드 표시명은 facets/선택 메타데이터에서 얻고 전체 상품 Map을 다시 만들지 않는다. 결과 집합이 바뀌면 이전 위치는 무효화하고 오래된 페이지/상세 응답은 적용하지 않는다.

기존 `file://` 실행도 유지한다. Worker가 허용되지 않는 환경에서는 같은 순수 모델과 분할 작업을 쓰는 대체 경로를 검증한다. 이 경로와 HTTP Worker의 결과는 같아야 하며 성능 보장은 구분한다.

### 4. 이력 묶음과 캐시에 상한

현재 2,000상품/브랜드 전체 묶음을 바이트 크기를 기준으로 나눈다. 파일 원문은 256KiB 이하로 나누고, 단일 거대 이력도 날짜 구간으로 나눈다. 상세 기본 기간은 해당 상품의 최신 가격 관측일을 끝으로 한 최근 90일이며 전체 기간은 사용자가 선택할 때 추가 요청한다. 과거 이력은 삭제하지 않는다. 경계 이전 마지막 가격은 이월 기준으로 별도 전달하며 새로운 실제 관측 행으로 꾸미지 않는다.

성공한 이력 파일은 LRU로 관리하며 초기 목표 16MiB 원문 캐시 상한을 둔다. 표시 중인 상품에 필요한 데이터와 진행 중 요청은 중복/퇴출 경쟁을 피한다. 상한은 JS heap 전체 상한을 뜻하지 않는다. 빌드의 이력 읽기도 상품/범위별로 나눠 전체 과거 행을 한 번에 읽는 동작을 없앤다.

### 5. 검증과 반영

전후 측정은 같은 DB/빌드 입력에서 먼저 비교하고 이후 공개 사이트도 별도로 측정한다. 전체 상품 식별·가격·출처·정렬·집계 동등성, 직접 링크, 지연 응답, 실패/재시도, HTTP/file 실행을 회귀 검증한다. 1년 분량 합성 이력으로 첫 목록 데이터 크기가 이력 수에 비례해 증가하지 않는지와 이력 파일/캐시 상한을 확인한다. 합성 데이터는 가격 정확도 검증으로 해석하지 않는다.

첫 목록 표시의 선행 조건에 전체 인덱스 다운로드가 없어야 한다. 첫 목록까지 이력 요청과 HTML에 포함된 이력 행은 0개, 초기 카드 120개 이하, 가격/출처/쿠폰 경고 보존을 필수 수용 조건으로 둔다. 백그라운드 인덱스 다운로드는 첫 목록 표시 후 시작할 수 있다. 네트워크 속도에 의존하는 절대 로딩 시간은 사전 보장하지 않고 실제 결과를 기록한다. 전체 검색 준비 시간, 압축 전송량, 긴 작업과 메모리도 함께 보고한다.

기존 일일 수집 성공 후 Pages 자동 배포 연결은 유지한다. 개선 구현·검증·배포 후 결과 Markdown을 갱신한다. 문제가 있으면 이전 배포 소스로 되돌릴 수 있도록 DB 형식/이력은 변경하지 않는다.

## 구현자의 선택과 범위 밖

첫 120개, 256KiB 이력 묶음, 16MiB 캐시는 승인된 권장 설계의 시작값이다. 성능과 호환성 검증에서 조정이 필요하면 이유와 영향을 기록한다. 별도 서버/API, 유료 서비스, 수집 대상 확대, 원본 이력 삭제, 가격 정확도 정책 변경, 전면 UI 재설계는 범위 밖이다.

독립 검토에서 지적한 기존 inline 이력 누적과 Worker 전환 후 전체 상품 직접 접근 계약을 위 내용에 보완했다. 사용자에게 남길 제품 선택 질문은 없다.
