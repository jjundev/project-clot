# 대시보드 배포 메모리 문제 수정 설계

## 의도와 결정 상태

전체 상품과 가격 이력을 유지하면서 현재 Release DB 로 대시보드 생성과 검증이 메모리 부족 없이 완료되게 한다. 기존 조회와 Pages 흐름을 고치는 bounded 작업이다. 2026-10-25 grill-yourself 설계의 결정 #1–#7 을 따른다. 사용자가 후속으로 writing-plans 를 호출했으므로 #8 의 권장 범위인 **조회 오류 수정과 재발 검증까지**를 confirmed by default 로 기록한다. 2026-10-25 사용자가 Native 구현과 실데이터 생성·검증을 승인했다. 이 문서와 계획 저장은 구현·커밋·원격 변경 허가를 뜻하지 않는다.

## 조사 근거

- 조사 당시 HEAD: `c3ca69af222f37c616797da2f55eaa788a2aebe5`.
- 최근 실패: https://github.com/jjundev/project-clot/actions/runs/40102747613/job/120898080493 . `visualize --no-open`의 SQLite `.all()`에서 약 4GB 힙 한계로 종료 코드 134 가 발생했다. 검증기와 업로드는 실행되지 않았다.
- 마지막 성공: https://github.com/jjundev/project-clot/actions/runs/40082610770/job/120839077616 . 전체 430,353 개, 4910 128,611 개가 검증됐다. 이 수치는 당시 스냅샷의 값이며 새 완료 기준의 고정 기대값이 아니다.
- 같은 코드의 다음 실행부터 실패했고 4910 DB 는 1,203,073,024 바이트에서 1,274,224,640 바이트로 증가했다. 최근 실패에서는 1,309,908,992 바이트였다.
- 실제 DB 의 브랜드 751: ACTIVE 65 개, 번호 범위 5,071,959–77,241,701. 기존 범위 조회는 1,174,195 행과 증빙 약 753.2MiB 를 읽었고 해당 브랜드 조회는 574 행과 약 0.4MiB 였다.
- 512MiB 제한 단독 실험에서 기존 조회는 OOM, 브랜드 제한 조회는 힙 약 5MiB 로 성공했다. 전체 수정 빌드의 메모리는 아직 측정하지 않았다.
- `src/visualizer.js:489`는 브랜드마다 최대 200 개를 처리하지만 `src/site4910/price-validation.js:40`의 범위 분기는 브랜드 조건을 무시한다.
- `scripts/verify-dashboard-build.js:149,198`은 모든 asset 과 history 를 유지한다. 추가 위험이지만 현재 실패 지점은 아니다.

## 전역 제약

- Node.js 24, ESM, node:sqlite, node:test 와 기존 Playwright 구성을 사용하고 새 의존성을 추가하지 않는다.
- 전체 상품·전체 날짜별 가격 이력·가격 보정·최저가·하락 판정·공개 대시보드 v2 형식은 유지한다.
- DB 스키마·수집·이력 보관 정책·검증 증빙 원본은 변경하지 않는다.
- 운영 데이터 파일과 기존 미추적 `data/4910-all.js`는 수정·삭제·스테이징하지 않는다.
- 생산 경로의 상품 묶음과 목록 조회 SQL 의 상품 ID 수는 각각 최대 200 개로 유지한다.
- 실제 데이터의 생성과 검증은 각각 `--max-old-space-size=4096`으로 통과해야 한다. 힙 상한 증설이나 검증 생략으로 통과시키지 않는다.
- 회귀 메모리 실험은 자식 프로세스의 `--max-old-space-size=512`에서 수행한다.
- 기존의 선택적 4910 누락·부분 실패 안내와 롤백 동작은 유지하되, 실데이터 완료 검증에서는 4910 포함과 `scanState=complete`를 요구한다.

## 조회 계약

기존 `readPriceValidations(db, kind, options = {})`에 `snos: number[] | null = null`, `includeEvidence: boolean = true`를 추가한다. 기존 옵션 `brandSno`, `sno`, `snoFrom`, `snoTo`는 유지한다.

- 주어진 조건은 모두 AND 로 적용한다. 브랜드와 번호 범위가 함께 주어져도 어느 조건도 버리지 않는다.
- `snos=null`은 기존의 목록 제한 없는 모드다. `snos=[]`는 빈 Map 이며 검증 행 조회를 실행하지 않는다.
- 목록은 중복 제거 후 최대 200 개씩 분리해 placeholder 로 바인딩한다. DB 에서 얻은 숫자 ID 를 전달하며 문자열 보간으로 값을 SQL 에 넣지 않는다. 목록의 중복 때문에 같은 이력을 여러 번 읽지 않는다.
- `snoFrom` 또는 `snoTo` 중 하나만 있거나 역전된 범위는 RangeError 로 거부한다. `snos`에 양의 안전한 정수가 아닌 값이 있으면 TypeError 로 거부한다. 잘못된 필터를 전체 조회로 완화하지 않는다.
- 검증 테이블이 없으면 기존대로 빈 Map 을 반환한다. 정상 호출에서 키는 `${sno}:${date}`, 값은 SQLite row 다. Map 삽입 순서는 공개 계약이 아니다.
- 결과는 `.iterate()`로 Map 에 직접 적재한다. 반환 Map 에 필요한 행은 남으므로 무제한 조회 모드 자체가 상수 메모리라는 보장은 하지 않는다.
- `includeEvidence=true`는 기존 전체 row 필드를 제공한다. `false`는 `kind,sno,date,status,corrected_json,reason,checked_at`만 SELECT 하며 `evidence_json` 속성은 반환하지 않는다.

## 대시보드 연결

`buildScan4910Payload()`가 ACTIVE·브랜드·번호 범위·찜 제외 조건으로 얻은 실제 `goods`의 ID 를 `snos`로 전달하고 `includeEvidence:false`를 지정한다. 모든 호출 형태에서 동일하게 적용한다. 외부 함수 시그니처와 반환 payload 는 변경하지 않는다. 200 개 생산 묶음은 한 번의 검증 이력 SQL 로 읽고, 전체 브랜드를 읽는 기존 호출은 내부 목록 분할을 사용한다.

가격 계산은 그대로 둔다. 찜 export 와 `scripts/4910-price-revalidate.js`는 기본 증빙 포함 모드를 계속 사용한다. 스캔 경로가 제외된 상품의 `corrected_json`을 처리하지 않도록 조회 단계에서 차단한다.

## 테스트와 관측

- 공통 조회: 필터 교집합, 빈 목록, 중복 ID, 201 개 이상의 목록, 잘못된 입력, 없는 테이블, 증빙 포함 기본값과 제외 옵션을 검사한다.
- 생산 연결: 희소한 대상 ID 사이에 다른 브랜드·비활성·찜 상품을 놓고 실제로 읽힌 검증 key 와 완성된 가격 이력을 검사한다. 결과만 맞고 불필요한 이력을 읽는 구현도 실패해야 한다.
- 메모리: 임시 파일 DB 에 무관한 상품의 큰 증빙을 넣고 별도 프로세스에서 대상 묶음을 읽는다. 512MiB 제한의 정상 종료와 대상 ID·가격 이력 보존을 검사한다. 생성 fixture 나 전체 증빙을 stdout 에 출력하지 않는다.
- 기존 가격 검증·재검증·대시보드 테스트와 브라우저 테스트를 실행한다. 새 test 파일은 `import './setup-env.js';`로 시작한다.
- Pages 트리거에 `src/site4910/price-validation.js`를 추가하고 배포 전 node:test 목록에 가격 검증 테스트를 포함한다.
- 생성과 검증을 별도 named step 으로 분리한다. 생성 step 에 기존 wide 필수 조건과 적립금 opt-in 환경변수를 유지한다. Ubuntu 의 `/usr/bin/time -v`로 각 Node 프로세스 최대 RSS(KiB)와 실행 시간을 기록하고 실패 종료 코드를 전파한다.
- RSS 는 OS 가 관측한 프로세스 메모리이며 V8 힙 상한과 같은 수치가 아니다. RSS 의 임의 수치를 완료 기준으로 새로 만들지 않는다.

## 실데이터 완료 기준

고정한 watched·4910·Musinsa wide 스냅샷의 날짜·바이트·SHA-256 을 기록한다. 원본은 보존하고 watched DB 는 임시 복사본을 사용한다. 동일한 입력으로 생성과 전체 asset/history 검증을 각각 4GiB 힙 제한에서 통과시킨다. 상품 수와 전체 ID 집합은 같은 SQL 대상·중복 제거 규칙으로 독립 계산하고, 작은 adversarial fixture 에서는 모든 가격 이력의 예상값도 비교한다. 과거 성공 시점의 상품 수를 현재의 기대값으로 쓰지 않는다.

4910 이 빠진 채 성공한 subtotal 은 완료가 아니다. 두 단계의 시간·최대 RSS 와 입력 hash 를 검증 기록에 남긴다. 실제 Pages 게시 확인은 구현 통합·배포가 승인된 뒤에만 수행하며, 로컬 성공과 원격 게시 성공을 구분한다.

검증기 전체 재설계, 러너 교체, 힙 증설, 이력 삭제, DB/Release 구조 개편, UI 변경. 생성 수정 후 검증기 OOM 이 확인되면 입력과 측정값을 기록하고 설계를 다시 정한다. 검증 생략이나 데이터 축소로 완료 처리하지 않는다.
