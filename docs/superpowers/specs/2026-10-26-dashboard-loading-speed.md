# 상품 로딩 속도 개선과 로딩 화면

2026-10-26 KST. grill-yourself 설계(B안)를 보존한다. Needs-you 3건(N1–N3)은 사용자가 별도 값을 주지 않아 권장안으로 확정(confirmed by default)했다. 2026-10-17 범위별 로딩 설계(`2026-10-17-scoped-dashboard-loading.md`)의 "동시 4개"와 "검색 준비 중 · 기본 상품 미리보기" 규칙을 이 문서가 대체한다.

## 실측 근거 (실사이트, Chrome headless, 무제한 네트워크)

| 시나리오 | 첫 카드 | 검색 완료 | 인덱스 파일 | 압축 전송 |
|---|---:|---:|---:|---:|
| 전체·전체 기본 | 0.13초 | 9.3–9.7초 | 1,006 | 23.5MB |
| 무신사·상의 | 0.12초 | 1.4–1.5초 | 116 | 3.0MB |

- 같은 1,006개 파일을 Node로 받을 때 동시 4개 5.8초, 8개 2.4초, 16개 2.0초다. 사이트는 HTTP/2다.
- 전체 505,853행의 eval+unpack CPU는 2.6초다.
- 기본 조건(과거 기록 미포함)은 `!fresh` 상품을 제외한다. 빌드 시점에 fresh일 수 있는 행은 최대 119,271개(23.6%)다.
- 빌드 시점의 기본 결과는 보수적으로 계산해도 최소 13.3시간 동안 바뀌지 않는다.

## 동작

1. **기본 화면 즉시 확정.** 저장 조건이 출처별 기본 조건(`previews[src].state`)과 같고 현재 시각이 `[asOfMs, exactUntilMs)` 안이면 빌드 미리보기의 첫 120개와 집계를 확정 결과로 표시한다. 로딩 화면과 `—`가 없다. 검색 인덱스는 load 이후 유휴 시간에 백그라운드로 받아 "더 보기"와 조건 변경에 대비한다.
2. **live/history 인덱스 분할.** 인덱스를 출처 × 카테고리 × tier로 나눈다. `live`는 빌드 시점 이후 한 번이라도 fresh일 수 있는 상품, `history`는 그 외다. 과거 기록 미포함 질의는 live만 받는다. 과거 기록 포함은 history를 추가로 받고 이미 받은 파일은 재사용한다. 기기 시계가 빌드 시점보다 이르면 모든 tier를 받는다.
3. **동시 다운로드 8개.** scoped 경로의 동시 다운로드 상한을 4에서 8로 올린다.
4. **로딩 화면.** 사용자 조작으로 조건이 바뀌면 기존 카드를 흐리게 한다. 150ms 안에 결과가 없으면 스켈레톤 카드 12개(shimmer)와 그리드 위 2px 진행 막대(받은 파일 / 필요한 파일, 모르면 indeterminate)로 바꾼다(N3). 저장 조건이 기본이 아닌 첫 접속도 같은 스켈레톤을 쓰며 조건과 다른 미리보기 카드는 보여주지 않는다(N1). 보이는 진행 문구는 없다. 스크린리더용 숨김 텍스트 "상품을 불러오는 중"(role=status)과 그리드 `aria-busy`만 둔다(N2).
5. **주기적 갱신.** 60초 갱신, 탭 복귀, bfcache 복귀는 화면을 스켈레톤으로 바꾸지 않는다.
6. **문구 제거.** "검색 준비 중 · 기본 상품 미리보기", "검색 준비 중 · 이전 검색 결과 표시", "검색 준비 중"을 표시하지 않는다. 빌드 공지와 상세 공지는 유지한다.
7. **실패.** 그리드 자리에 "상품을 불러오지 못했습니다"와 [다시 시도]를 표시하고 건수는 `—`다.
8. **상품번호 조회 중**에는 스켈레톤 카드 1개를 보여준다. **"더 보기" 요청 중**에는 버튼에 스피너와 "불러오는 중"을 보여준다.
9. reduced-motion에서는 기존 전역 규칙에 따라 정적 스켈레톤을 보여준다.

## 정확성 규칙

- `freshWindow(x)`는 `priceSignalEligibility`와 같은 정적 조건을 만족할 때 `{from: max(at, saleAt), until: min(at, saleAt) + PRICE_TTL_MS}`, 아니면 `null`이다. 모든 시각 t에서 `refresh(x,{asOfMs:t}).fresh === (from <= t && t <= until)`이다.
- tier: `freshWindow(x)?.until >= asOfMs`이면 live.
- `exactUntilMs`: live 항목마다 `from > asOfMs ? from : until`을 구한 값 중 최솟값. live가 없으면 `asOfMs + PRICE_TTL_MS`.
- 결과·순서·페이지·집계는 기존 `queryCatalog`와 같다.

## 유지

GitHub Pages 정적 호스팅, HTTP Worker와 file:// 대체 경로, 자산 256KiB 이하, 요청 15초 제한, 미확인 건수 `—`, 직접 링크 경로, 상세 이력 계약을 유지한다. DB·수집·가격 정책은 바꾸지 않는다.

## 이번 범위 밖

인덱스 행 압축, 텍스트 역색인·검색 서버, 내용 해시 기반 배포 간 캐시, 브랜드 대화상자의 "브랜드 검색 준비 중…" 문구.

## 수용 기준

- 인덱스 응답을 지연시켜도 기본 화면의 건수가 숫자로 바로 나온다.
- 과거 기록 미포함 질의는 history 파일을 요청하지 않는다.
- 동시 요청은 최대 8개다.
- 진행 이벤트는 현재 질의에만 반영된다.
- 주기적 갱신은 스켈레톤을 띄우지 않는다.
- 같은 측정 스크립트로 개선 전후의 전체·전체 기본, 전체·전체 검색어, 무신사·상의, 과거 기록 포함 시나리오를 기록한다. 절대 시간은 보장하지 않는다.
